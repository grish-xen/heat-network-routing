# Инструкции для работы с проектом

- Актуальные правила находятся в `docs/reference/current-technical-appendix.docx` и `docs/reference/clarifications.docx`; краткая сводка — `docs/RULES.md`. При противоречии со старым PDF применяйте актуальное техническое приложение.
- Не переносите из старой модели `oks_future`, `upstream_object_id`, расчёт реконструкции существующей сети или выходной объект `tie_in` в обязательный режим.
- Координаты, число объектов, ID и конкретную геометрию конкурсного GeoJSON нельзя зашивать в алгоритм. Проверка будет на другом наборе той же структуры.
- Все изменения межмодульных типов и соглашений сопровождайте обновлением `docs/DATA_MODEL.md` и `docs/MODULE_CONTRACTS.md`.
- Для расчётов расстояний используйте EPSG:32637; вход и выход GeoJSON — WGS 84. Единицы расходов — т/ч, длин — м, стоимости — руб.
- Не объявляйте модуль готовым по успешной работе только на конкурсном файле: проверяйте простые искусственные случаи и ошибки входных данных.
- Общие Java-типы и интерфейсы уже существуют: версия контракта 1.0. Используйте их; описание поведения находится в `docs/MODULE_CONTRACTS.md`. Числовые справочники едины для всех модулей: `backend/src/main/resources/rules/catalog-v1.json`.
- Внутренние JTS-геометрии — EPSG:32637. Простое изменение SRID не преобразует координаты. Тип входного ID сохраняется через `ObjectId`; внутренние строковые ID узлов не заменяют исходные ID при экспорте.
- После изменения Java запускайте `mvn -f backend/pom.xml verify` на JDK 11. После изменения контрактов, справочников или примеров — `python scripts/check_repository.py`.
- Реализованы health, запуск сервера и `input.GeoJsonInputParser` с временным дисковым Dataset. Использование и ограничения — `docs/INPUT_MODULE.md`. Product API из `contracts/openapi.json` помечен planned. Не выдавайте тестовые ответы за рассчитанные маршруты.
- Исходные новые DOCX также доступны как текст в `docs/reference/*.md`. При изменении оригинала обновляйте текстовую копию и проверяйте каталог.
