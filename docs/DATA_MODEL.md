# Модель команды — контракт 1.0

Точные Java-типы: `backend/src/main/java/ru/hackathon/heatnetwork/model/Model.java`, `ObjectId.java`, `Dataset.java`. Общие DTO находятся внутри класса `Model`, например `Model.RouteCandidate`. Это компактное начальное расположение типов; перенос в отдельные файлы согласуется общим PR.

## Координаты, ID и числа

- `InputParser` переводит геометрию WGS 84 в EPSG:32637. Реализация `GeoJsonInputParser` использует Proj4J 1.4.1. Внутренние геометрии — JTS `Point`, `LineString`, `Geometry` с SRID 32637. Простое присвоение SRID **не преобразует координаты**.
- `Dataset` предоставляет поиск по ID, поток объектов одного типа и пространственную выборку по прямоугольнику. Реализация может хранить данные на диске/в БД; нельзя требовать, чтобы файл до 3 ГБ целиком оказался в коллекции Java. Вызывающий закрывает потоки; координатор закрывает `Dataset` в конце работы.
- `ObjectId` хранит исходное число/строку для последующего экспорта. Число `1` и строка `"1"` различаются; числа `1` и `1.0` эквивалентны. Не переводить числовые ID через `double`.
- ID внутренних узлов и рёбер — строки. `Node.inputObjectId` связывает существующую камеру/точку подключения с входным объектом. Новая камера и технический узел этого поля не имеют. При экспорте новые ID должны быть уникальны среди всех вариантов и не совпадать с входными ID.
- Координаты и длины — `double` в метрах, ДУ — `int` в мм, расходы и деньги — `BigDecimal`. Поля `Double` глубины могут быть `null` в 2D.
- Командное численное соглашение: совпадение геометрических концов — до 0,001 м; оно не уменьшает нормативные отступы. Стоимости конечных объектов округляются до копеек `HALF_UP`, сводки суммируют эти стоимости. Score сохраняется минимум с 8 знаками после запятой; сравнение вариантов выполняется до округления отображаемых значений. Это технические соглашения команды, а не дополнительные правила организатора.

## Смысл сущностей

| Тип | Содержание |
| --- | --- |
| `InputObject` | Исходный ID, тип, метрическая геометрия, ДУ/расход/тип ограничения по виду объекта |
| `Node` | Внутренний ID, координата, вид узла, ссылка на входной объект при наличии |
| `Edge` | Внутренний ID, `fromNodeId`, `toNodeId`, линия с концами в этих узлах |
| `Attachment` | Корень компоненты и существующий объект присоединения: камера либо линия |
| `RouteCandidate` | Несколько деревьев новой сети, присоединения и ID целей, для которых путь не найден |
| `CalculatedEdge` | Конечный участок после деления: расход, ДУ, длина, способ, глубина, цена, ID пересечений |
| `CalculatedVariant` | Окончательные узлы и рёбра, новые камеры с ценой, присоединения, сводка |
| `Evaluation` | ID кандидата, допустимый вариант либо диагностика отклонения |

## Топология

Внутри команды рёбра направлены от присоединения к потребителю; координаты линии идут от `fromNodeId` к `toNodeId`. В выходном GeoJSON это лишь порядок записи, физическое направление не является требованием формата организаторов.

У каждой компоненты ровно один `Attachment`; его `rootNodeId` — камера. Если камера существующая, `existingObjectId` указывает на неё. Если новая — на входной `heat_network`, на котором стоит камера. Существующие трубы не добавляются как рёбра новой сети.

У корня нет родительского нового ребра, у остальных узлов ровно одно. Каждая точка подключения встречается один раз: как подключённый лист либо в `unconnectedPointIds`. Разветвляется только камера; при проверке четырёх примыканий учитываются и существующие участки. Повороты внутри LineString отдельными узлами не становятся.

## Передача и изменение объектов

Переданные DTO и JTS-геометрии получатель считает доступными только для чтения. Калькулятор создаёт свой конечный граф, потому что выделение специальных участков требует деления линий и технических узлов. При делении сохраняются связность, привязки к входу и непрерывные пути одного ДУ.

Внутренние JTS-типы не сериализуются прямо в HTTP API. `output` преобразует координаты и свойства в формат организаторов; `api` использует отдельные HTTP DTO по OpenAPI.

Реализация чтения и дискового Dataset, правила валидации и ограничения — [INPUT_MODULE.md](INPUT_MODULE.md). Сигнатуры контракта 1.0 сохранены.

HTTP-снимок задачи представлен `api.JobView`, ошибка — `api.ApiError` по существующим Job/Error в OpenAPI. `Diagnostic.inputObjectId`, `candidateId`, `segmentId` при наличии переходят в `Error.details[0]`; числовой ID сохраняет точность при записи статуса на диск. `FileJobStore` дополнительно хранит время изменения для очистки, но оно не добавляется в HTTP DTO. Жизненный цикл и текущие пределы — [JOB_API.md](JOB_API.md).
