# Загрузка и статусы задач

Участник 1 реализовал `POST /api/jobs` и `GET /api/jobs/{jobId}` по контракту 1.0. Файл сохраняется на диск, затем отдельный рабочий поток вызывает настоящий `InputParser`. Результат валидации доступен через статус задачи.

**Расчётные модули пока не подключены.** Корректный файл заканчивается `FAILED` с кодом `PROCESSING_UNAVAILABLE`. Это означает, что проверка файла пройдена, но расчёт недоступен. `SUCCEEDED` будет использоваться после завершения расчёта и экспорта. Карта, варианты и скачивание результата пока остаются planned; для них frontend продолжает использовать согласованные примеры.

## Проверить вручную

Из корня репозитория запустите backend:

```sh
mvn -f backend/pom.xml spring-boot:run
```

В другом терминале загрузите пример (в Windows PowerShell используйте `curl.exe` вместо `curl`):

```sh
curl -i -F "file=@test-data/synthetic/two-consumers/input.geojson" -F "mode=2d" http://localhost:8080/api/jobs
```

Сервер возвращает HTTP **202**, заголовок `Location: /api/jobs/<jobId>` и JSON:

```json
{
  "jobId": "00000000-0000-4000-8000-000000000001",
  "status": "QUEUED",
  "stage": "QUEUED",
  "mode": "2d",
  "diagnostics": []
}
```

ID выше иллюстративный: используйте значение из своего ответа.

```sh
curl http://localhost:8080/api/jobs/<jobId>
```

Либо откройте `/swagger-ui.html`: обе операции уже описаны и доступны для выполнения.

## Для frontend

1. Отправить `FormData` с одним файлом `file` и необязательным `mode`. При использовании браузерного `fetch` заголовок `Content-Type` формирует браузер вместе с multipart boundary.
2. После 202 запомнить `jobId`, опрашивать статус примерно раз в секунду. POST всегда возвращает снимок `QUEUED`, даже если обработка уже успела начаться.
3. Пока статус `QUEUED` или `RUNNING`, показывать ожидание и этап. Обработка может закончиться между опросами: наблюдать каждый промежуточный этап необязательно.
4. При `FAILED` остановить опрос и показать `diagnostics[].message`. При `PROCESSING_UNAVAILABLE` объяснить, что файл проверен, а расчёт пока недоступен. Не показывать готовые маршруты из тестового примера как результат загруженного файла.
5. `SUCCEEDED` / `DONE` зарезервированы для полной цепочки. Пример `job-succeeded.json` остаётся макетом будущего успешного расчёта.

Новые примеры: `test-data/api/job-queued.json`, `job-invalid-input.json`, `job-processing-unavailable.json`. JSON-форма существующих полей сохранена. GET отдаёт `Cache-Control: no-store`.

| HTTP-код при запросе | Что означает |
| --- | --- |
| 202 | Файл сохранён, задача принята; содержимое ещё может оказаться ошибочным |
| 400 | Нет файла, пустой/лишний файл, неизвестный/пустой/повторный mode или повреждённый multipart |
| 413 | Превышен предел файла либо всего multipart-запроса |
| 415 | Запрос не в формате multipart/form-data |
| 422 | `depth` пока не поддерживается; отсутствие mode означает `2d` |
| 503 | Заполнена очередь или сервер останавливается; `Retry-After: 5` |
| 404 при GET | Неизвестный, некорректный или уже удалённый по сроку ID |
| 500 | Ошибка хранения или внутренняя ошибка выполнения HTTP-запроса |

Ошибки HTTP имеют форму `{ "code": "...", "message": "..." }`. Ошибки содержимого GeoJSON появляются **после 202** в `diagnostics` задачи. При известных ссылках на объект добавляется `details: [{ "inputObjectId": ... }]`; число и строка сохраняют исходный тип и точность. Пути сервера и stack trace остаются в серверном журнале.

## Устройство и ограничения

- `JobController`, `JobView`, `ApiError`, `ApiExceptionHandler` — HTTP и перевод диагностики.
- `JobService` — приём, очередь, фоновая валидация, закрытие Dataset и очистка входного файла.
- `FileJobStore` — маленькие JSON-статусы на диске, замена через временный файл, восстановление после перезапуска и срок хранения. Это временная реализация хранилища задач; PostgreSQL пока не используется.
- `JobConfiguration` — servlet multipart с записью файла сразу на диск; приложение копирует его буфером 64 КиБ. Исходное имя файла не используется в путях, ID генерирует сервер.

| Настройка Spring | По умолчанию |
| --- | --- |
| `heat-network.jobs.storage-directory` | `${java.io.tmpdir}/heat-network-routing/jobs` |
| `heat-network.jobs.workers` | 2 параллельные обработки |
| `heat-network.jobs.queue-capacity` | 48 дополнительных мест |
| `heat-network.jobs.max-file-bytes` | 3 221 225 472 (3 ГиБ); можно уменьшить |
| `heat-network.jobs.retention` | `24h` после последнего изменения статуса |

Предел multipart-запроса равен пределу файла плюс 1 МиБ на оформление запроса. Настройки размера задаются через `heat-network.jobs.max-file-bytes`: `JobConfiguration` создаёт единый `MultipartConfigElement`, поэтому отдельные `spring.servlet.multipart.max-file-size` здесь не применяются.

Лимит 2 + 48 считает операции сохранения, уже принятые приложением, ожидающие задачи и выполняющиеся задачи. Servlet принимает multipart до этой проверки: лимит очереди не является общим лимитом HTTP-соединений или дисковой квотой. Проверки 3 ГиБ через HTTP и 50 одновременных пользователей ещё нужны; существующая проверка импорта файла 88,7 МБ в JVM с 64 МиБ heap относится к `InputParser`.

После обычного завершения или ошибки входной файл удаляется, Dataset закрывается. Статус хранится 24 часа; очистка выполняется раз в минуту, активные задачи исключены. При остановке сервера ожидающие и прерванные рабочие задачи получают `JOB_INTERRUPTED`. После аварийного перезапуска оставшиеся `QUEUED`/`RUNNING` становятся `FAILED` с `SERVER_RESTARTED`, входные файлы удаляются; автоматического продолжения нет. После аварийного завершения могут остаться временные файлы servlet/парсера: их полноценная очистка и дисковые квоты — отдельная задача эксплуатации.

Хранилище рассчитано на один экземпляр backend; файловая блокировка предотвращает второй запуск с той же папкой. Это не распределённая очередь. В Compose статусы находятся в томе `job-data`; локально они сохраняются, пока существует настроенная папка.

Переменная окружения для папки в Compose — `HEATNETWORK_JOBS_STORAGEDIRECTORY`. По [правилам Spring Boot](https://docs.spring.io/spring-boot/docs/2.6.x-SNAPSHOT/reference/htmlsingle/#features.external-config.typesafe-configuration-properties.relaxed-binding.environment-variables) точки становятся `_`, дефисы удаляются. Привязка переменной проверяется отдельным `JobConfigurationTest`.

## Следующая интеграция участника 1

В `JobService.Work.run()` после `parser.parse(...)` находится явная точка подключения координатора. Он должен передать открытый Dataset в существующие `RoutePlanner` / `VariantCalculator`, сохранить реальные варианты и завершить экспорт. Только после этого появится `SUCCEEDED` и будут реализованы операции результатов и карты. Закрытие Dataset остаётся обязанностью владельца жизненного цикла задачи; при добавлении карты нужно обеспечить доступ к её данным до истечения срока задачи.

`JobView` — HTTP DTO, он не заменяет общие типы `model.Model`. Новые статусы и обязательные поля не введены. Дополнительные строковые коды ошибок задокументированы в OpenAPI.

Основание реализации multipart: [контракт MultipartFile Spring 5.3](https://docs.spring.io/spring-framework/docs/5.3.0/javadoc-api/org/springframework/web/multipart/MultipartFile.html). Поток файла закрывает вызывающий код; `getBytes()` для загрузки не используется.
