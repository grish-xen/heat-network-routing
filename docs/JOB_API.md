# Задачи расчёта и результаты

## Замена файлов на Windows

Статусы, результаты и архивы карты публикуются заменой временного файла, по возможности атомарной. При `AccessDeniedException` выполняется до шести попыток с паузами 20, 40, 80, 160 и 320 мс: внешняя программа может кратковременно удерживать файл даже при сериализованном доступе внутри сервера. Старый файл заранее не удаляется. Постоянный отказ и другие ошибки ввода-вывода не скрываются; прерывание останавливает ожидание с сохранением interrupt-флага. Это ограниченный повтор, а не гарантия работы при постоянной блокировке каталога.

## Возможности

Реализована серверная цепочка: загрузка → проверка GeoJSON → поиск маршрутов → инженерный расчёт и пространственная проверка → отбор вариантов → экспорт.

## Проверить вручную

Из корня репозитория запустите `mvn -f backend/pom.xml spring-boot:run`. В другом терминале (Windows: `curl.exe`):

```sh
curl -i -F "file=@test-data/synthetic/two-consumers/input.geojson" -F "mode=2d" http://localhost:8080/api/jobs
curl http://localhost:8080/api/jobs/<jobId>
curl http://localhost:8080/api/jobs/<jobId>/variants
curl -o result.geojson http://localhost:8080/api/jobs/<jobId>/result
```

Используйте jobId из ответа загрузки. POST возвращает HTTP 202, Location и снимок QUEUED. Перед запросом результатов дождитесь SUCCEEDED / DONE. Операции доступны в Swagger `/swagger-ui.html`.

## Для frontend

1. Отправить FormData с одним `file` и необязательным `mode=2d` либо `mode=depth` (по умолчанию 2d). Content-Type с boundary формирует браузер.
2. После 202 опрашивать статус примерно раз в секунду, пока он QUEUED или RUNNING.
3. Этапы: VALIDATING, затем повторяющиеся ROUTING / CALCULATING, затем EXPORTING. Опрос может пропустить промежуточные этапы.
4. При SUCCEEDED получить `/variants`; скачать весь GeoJSON через `/result` обычной ссылкой. Сводки содержат официальные snake_case поля и идут по возрастанию score. Идентификаторы, ранги и числовые значения совпадают со сводками в файле.
5. При FAILED показать диагностику и прекратить опрос. Частичное подключение может быть SUCCEEDED: неподключённые точки перечислены в `unconnected_oks_ids`, штраф включён в расчёт. Диагностика ROUTE_NOT_FOUND поясняет ограничение лучшего варианта.

Реализована [карта `/map`](MAP_API.md): исходные объекты и геометрия выбранного варианта по bbox, с постраничной выдачей. Режим `VITE_API_MODE=http` обращается к реальным операциям сервера. Fixture остаётся отдельной демонстрацией. Результаты браузерной проверки — [INTEGRATION_CHECK.md](INTEGRATION_CHECK.md); воспроизводимая HTTP-проверка — [API_SMOKE_TEST.md](API_SMOKE_TEST.md).

| HTTP-код | Смысл |
| --- | --- |
| 202 POST | Файл сохранён, задача принята; содержимое ещё может быть ошибочным |
| 400 | Нет файла, пустой/лишний файл, неверный/повторный mode или повреждённый multipart |
| 413 | Превышен размер файла или multipart-запроса |
| 415 | Загрузка не multipart/form-data |
| 503 | Очередь заполнена или сервер останавливается; Retry-After: 5 |
| 404 GET | Неизвестный, некорректный или удалённый по сроку jobId |
| 409 результаты | Задача выполняется либо завершилась ошибкой (RESULT_NOT_READY) |
| 500 | Ошибка хранения или внутренняя ошибка запроса |

Ошибки HTTP: `{ "code": "...", "message": "..." }`. Ошибки GeoJSON появляются после 202 в diagnostics. Ссылки на входные объекты идут в details; числовой/строковый тип и точность ID сохраняются. Внутренние пути и stack trace остаются в журнале сервера. GET-ответы имеют Cache-Control: no-store; скачивание — application/geo+json, Content-Disposition attachment и Content-Length.

## Координатор и отбор

CalculationCoordinator открывает RoutePlanner.SearchSession. Каждый кандидат передаётся VariantCalculator, результат — обратно через feedback, затем поиск продолжается до конца сессии или max-candidates. Режим Job передаётся поиску и калькулятору. Калькулятор сам вызывает SpatialValidator. Диагностика поискового бюджета сохраняется и при SUCCEEDED; наличие результата не скрывает остановку по лимиту.

- Отклонение кандидата не останавливает поиск. Внутреннее исключение завершает задачу с INTERNAL_ERROR.
- Если допустимых вариантов нет, возвращается FAILED / ROUTE_NOT_FOUND и до 20 диагностик отклонения. Завершение бюджета не доказывает техническую невозможность подключения.
- Вариант со всеми точками неподключёнными допустим, если такой кандидат после поиска сформирован маршрутизатором и принят калькулятором. Координатор сам его не создаёт.
- Промежуточный частичный вариант исключается, если найден вариант, подключающий все его точки и дополнительные. Снижение стоимости не служит основанием для такого отказа от подключения.
- Оставшиеся варианты ранжируются по score. Дубликаты определяются без служебных ID и порядка списков, по геометрии с точностью 1 мм, параметрам рёбер, режиму, точным глубинам направленных рёбер и присоединениям. В памяти остаются не более трёх графов. Если ранее отброшенные варианты были вытеснены более полным подключением, вариантов может остаться меньше трёх.
- Публичные variant-1 … variant-3 действуют внутри задачи. Исходные Evaluation не изменяются. Цена и score повторно не рассчитываются.

## Хранение и публикация

Если итоговый статус не удаётся сохранить даже после коротких повторов записи файла, сервис удерживает небольшой снимок результата завершения и повторяет запись каждые пять секунд. Задача продолжает занимать слот приёма и исключается из очистки по сроку до успешной записи; это ограничивает число ожидающих снимков ёмкостью очереди. Графы и Dataset не удерживаются, расчёт не выполняется повторно. До сохранения SUCCEEDED результаты остаются недоступны. При штатной остановке выполняется ещё одна попытка записи. Снимки в памяти не переживают аварийное завершение процесса: если запись так и не состоялась, следующий запуск обработает задачу как незавершённую (SERVER_RESTARTED). Постоянная неисправность диска требует устранения причины; новые задачи могут получать QUEUE_FULL.

FileJobStore сохраняет `<jobId>.json` (статус), `<jobId>.result.geojson` (экспорт), `<jobId>.variants.json` (сводки). Запись идёт через временные файлы. Сводки извлекаются потоковым чтением экспорта с пропуском геометрии; JTS-объекты в HTTP не сериализуются.

SUCCEEDED записывается после экспорта, сохранения сводок, построения архивов карты и закрытия Dataset. До этого результаты недоступны; при ошибке частичные файлы удаляются. Превышение 500 МиБ даёт OUTPUT_LIMIT_EXCEEDED. Скачивание идёт потоком; его закрывает Spring. Если Windows не позволяет удалить файл во время скачивания, очистка повторится позже.

Перед удалением входного файла строится отдельный дисковый архив карты; архив результата строится из экспорта. Входной файл удаляется, временный Dataset закрывается. Архивы карты сохраняются до истечения срока задачи, подробности — [MAP_API.md](MAP_API.md).

## Настройки

| Spring-настройка | По умолчанию |
| --- | --- |
| heat-network.jobs.storage-directory | ${java.io.tmpdir}/heat-network-routing/jobs |
| heat-network.jobs.workers | 2 |
| heat-network.jobs.queue-capacity | 48 |
| heat-network.jobs.max-file-bytes | 3 221 225 472 (3 ГиБ) |
| heat-network.jobs.retention | 24h |
| heat-network.jobs.max-candidates | 100 |
| heat-network.jobs.search-seed | 0 |

Предел multipart-запроса — предел файла плюс 1 МиБ. JobConfiguration создаёт единый MultipartConfigElement; отдельные spring.servlet.multipart.max-file-size здесь не применяются. Лимит 2 + 48 включает сохраняемые загрузки, очередь и выполняющиеся задачи; это не дисковая квота и не лимит HTTP-соединений. В Compose папка задаётся через HEATNETWORK_JOBS_STORAGEDIRECTORY; файлы находятся в томе job-data.

Статусы и результаты очищаются раз в минуту по сроку последнего изменения статуса, активные задачи исключены. При остановке ожидающие и прерванные задачи получают JOB_INTERRUPTED. После аварийного перезапуска незавершённые задачи получают SERVER_RESTARTED, их результаты удаляются; успешные результаты сохраняются. Если у успешной задачи утрачен файл результата или сводок, она получает RESULT_UNAVAILABLE. Автоматического продолжения расчёта нет. Хранилище рассчитано на один экземпляр backend и защищено файловой блокировкой каталога задач. При заданном `spring.datasource.url` (в Compose — всегда) статусы, диагностика и сводки вариантов хранятся в PostgreSQL: таблицы `heat_jobs` и `heat_job_variants` (точный JSON сводки плюс score, стоимость, длина и число неподключённых точек для запросов). Загрузки, результат GeoJSON и индексы карты остаются файлами в каталоге задач: так их можно обрабатывать потоково. Без БД те же метаданные пишутся JSON-файлами — это режим разработки и тестов.

## Проверки и оставшаяся работа

Тесты проходят настоящий HTTP multipart → маршрутизатор → калькулятор → экспорт → сводки и скачивание на two-consumers. Проверяются перезапуск, закрытие ресурсов, очередь, ранжирование, дубликаты, отсутствие публикации незавершённого экспорта и очистка по сроку.

Ещё нужны дисковые квоты и нагрузочные испытания 3 ГиБ / 50 пользователей на целевой машине. Маршрутизатор и валидатор пока загружают наборы объектов в память. Прерывание проверяется между вызовами модулей; мгновенная отмена внутри длительного вызова маршрутизатора не гарантируется. Проверки потокового парсера и экспортёра не доказывают готовность всей цепочки к предельной нагрузке.
