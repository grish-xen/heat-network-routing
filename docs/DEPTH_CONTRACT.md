# Контракт режима глубины — depth-contract-1

Статус: **соглашение для реализации и общий комплект примеров**. DEPTH пока не реализован; настоящий POST с `mode=depth` возвращает HTTP 422 / UNSUPPORTED_MODE. Успешные DEPTH-ответы из `test-data/api/depth` — демонстрационные данные для разработки. Этот PR не включает режим.

Версия Java-интерфейсов и основного HTTP-контракта остаётся 1.0. Дополнение `depth-contract-1` определяет семантику существующих полей; новых полей Model не требуется. Владельцы модулей проверяют соглашение в PR до интеграции. При изменении допущений обновляются policy, примеры и этот документ вместе.

## 1. Владельцы и последовательность

1. №1 передаёт Dataset и SearchOptions(mode=DEPTH) в существующий RoutePlanner.
2. №2 выдаёт плановый RouteCandidate. Геометрии EPSG:32637; направление ребра — от присоединения к потребителю. Кандидат не содержит фиктивных глубин.
3. №3 выбирает ДУ, определяет специальные интервалы, строит профиль, делит граф, считает стоимость. **Построитель профиля принадлежит calculation.**
4. №3 передаёт окончательный CalculatedVariant в SpatialValidator участника 2. Проверяются окончательные габариты, глубины, уклон, связность и прежние плановые ограничения.
5. №3 возвращает Evaluation: variant!=null только при допустимом результате; при отказе variant=null и содержательные diagnostics. Переданные DTO не изменяются.
6. №1 передаёт feedback маршрутизатору, отбирает варианты одного режима, экспортирует, сохраняет и открывает результаты по HTTP. Разные профили глубины учитываются при дедупликации.

Построение профиля не заменяет независимой проверки. При отказе №2 ищет другой план или присоединение в пределах бюджета. Исчерпание бюджета не доказывает невозможность подключения.

## 2. Семантика профиля

- Глубина h — метры **до верха расчётного габарита**, положительное направление вниз от условной поверхности z=0. При высоте H верх имеет z=−h, низ z=−(h+H).
- `depthStartM`/`depthEndM` соответствуют первой/последней координате и fromNodeId/toNodeId. В GeoJSON — `depth_start`/`depth_end` и start_node_id/end_node_id.
- В 2D оба значения null. В DEPTH оба — конечные числа >=0,7. Boolean, null, NaN, Infinity и строки недопустимы.
- Внутри конечного ребра `h(s)=h_start+(h_end-h_start)*s/L`. s и L — накопленная и полная горизонтальная длина **в метрах EPSG:32637**. Геометрическая вершина не означает равную долю длины.
- Уклон `abs(h_end-h_start)/L <= 0.10`. Рёбра нулевой длины недопустимы. При смене уклона требуется деление; средний перепад всего пути не заменяет проверки частей.
- Смена способа прокладки, уклона, пересечение отметки 3 м создают границу конечного участка. Если здесь уже камера/потребитель, узел сохраняется; иначе создаётся TECHNICAL_NODE без стоимости и без ветвления.
- Деление не обнуляет ограничение длины непрерывного пути одного ДУ. Стоимость и ДУ камеры определяются прежними правилами.
- Плановый допуск совпадения узлов — прежние 0,001 м. Численный допуск сравнения глубин в стыках — 1e−6 м. Это допуск арифметики, не разрешение уменьшать нормативные отступы.

### Допущения команды для первой реализации

Эти решения позволяют работать параллельно, но требуют просмотра №2 и №3; при уточнении организаторов пересматриваются.

| ID | Допущение | Последствие |
| --- | --- | --- |
| P1 | Верх новой сети у корня и потребителя — 3 м | Во входе глубины точек отсутствуют. Фиксация концов может исключить короткий маршрут без места для перехода |
| P2 | В камере/техническом узле совпадает глубина **верха** примыкающих новых участков | При разных ДУ оси/низы различаются; это не детальная модель устройства камеры. При врезке применяется P1 |
| P3 | В пределах полной требуемой протяжённости спецпрохода глубина постоянна, переходы снаружи | Консервативная трактовка прямого прохода; при наложениях выполняются все ограничения |
| P4 | Новые трассы не пересекаются в плане вне общего узла даже при разных глубинах | Многоуровневые пересечения новых трасс пока не ищутся |

P1–P4 записаны в отдельной policy. Их нельзя представлять как требования организатора. Максимальную глубину и дискретный шаг контракт не вводит.

## 3. Пересечения

При верхе препятствия h_obj, его высоте H_obj, высоте новой сети H_new и просвете c:

```text
выше: h_new + H_new <= h_obj - c
ниже: h_new         >= h_obj + H_obj + c
```

Проверяется вся область взаимного перекрытия расчётных габаритов, а не только точка пересечения осей. При P3 профиль спецпрохода постоянный. Для дороги/трамвая проверяется минимальная глубина верха. Плановые углы, границы проходов и Kспец продолжают действовать. Парк, вода, железная дорога и другие запрещённые пересечения не становятся допустимыми при заглублении.

Газ: верх 2,8, высота 0,4, просвет 0,2 м; ниже нужно h>=3,4. Для новой сети ДУ80 высотой 0,16 сверху нужно h<=2,44; пример gas-above выбирает 2,40. Для существующей сети ДУ300 высота 0,45, поэтому ниже требуется h>=3,95. Диаметр 0,30 м не заменяет расчётную высоту.

## 4. Стоимость

`L_horizontal * tariff(DU) * K_special * K_depth`. На равномерном спуске/подъёме среднее Kгл концов применяется **после** деления на глубине 3 м. Наложение Kспец, камеры, врезки, штраф и score — по общим правилам.

Каждый конечный участок округляется до копеек HALF_UP, затем стоимости складываются. Денежные расчёты — BigDecimal. API и frontend цену не пересчитывают. Пространственная длина наклонной трубы не заменяет горизонтальную длину для расчёта.

`profile-units.json` содержит независимые контрольные суммы: 20 м от глубины 2 до 4 м при ДУ80 стоят 1 712 365,00 руб. без камер/врезок; деление на отметке 3 м обязательно.

## 5. Ошибки

| Код | Значение |
| --- | --- |
| DEPTH_VALUE_INVALID | Отсутствующая, неконечная, слишком малая глубина или неверный тип |
| DEPTH_CLEARANCE_VIOLATION | Недостаточная глубина под поверхностным объектом или вертикальный просвет |
| DEPTH_SLOPE_VIOLATION | Превышен уклон |
| DEPTH_CONTINUITY_VIOLATION | Разрыв глубины в стыке, нарушение P1 или постоянства прохода P3 |
| DEPTH_PROFILE_NOT_FOUND | Не найден допустимый профиль данного кандидата при принятых правилах и policy |
| SEARCH_BUDGET_EXHAUSTED | Поиск остановлен лимитом; это не доказательство невозможности |

Плановые ошибки сохраняют прежние коды. Diagnostic содержит message и по возможности inputObjectId, candidateId, segmentId. В HTTP ссылки находятся в details[]; тип исходного ID сохраняется.

Отказ кандидата передаётся через Evaluation и не завершает задачу немедленно. При наличии допустимого итогового варианта возможен SUCCEEDED с диагностикой ненайденных подключений; без допустимых вариантов — FAILED. При исчерпании бюджета и наличии результата сохраняется допустимый результат с явной диагностикой причины остановки. HTTP 422 относится к неподдерживаемому режиму при создании задачи, а не к каждому отказу кандидата.

Все рёбра успешного DEPTH-варианта имеют числовые глубины. Отсутствующий профиль нельзя подменить null или постоянными 3 м ради успешного статуса.

Координатор может определить достижение собственного maxCandidates по счётчику. Для внутренних ограничений №2 передаёт диагностику в существующем RouteCandidate.diagnostics (в том числе у последнего частичного/пустого кандидата); №1 должен сохранить её отдельно от отклонений калькулятора. Пустой Optional сам по себе не различает причины завершения: если явной диагностики нет, нельзя выдумывать SEARCH_BUDGET_EXHAUSTED. Расширение SearchSession для более подробного отчёта, если понадобится, оформляется отдельным изменением контракта.

## 6. HTTP и визуализация

Новых маршрутов HTTP нет. `mode=depth` уже зарезервирован в POST /api/jobs. `/variants`, `/result`, `/map`, `/map/bounds` используют прежние пути и пагинацию. Режим читается из Job; в официальный variant_summary он не добавляется. Варианты разных режимов не ранжируются вместе.

MapFeature.properties явно описывает глубины и ссылки на узлы; общая схема остаётся совместимой с input. Для новой теплосети DEPTH действует полная схема DepthNetworkProperties. Point-объекты не получают выдуманной глубины: их положение в сцене определяется примыкающими рёбрами по P2.

Для №4 выбран **статический генерируемый ресурс** `contracts/visualization-rules.v1.json` со схемой `visualization-rules.schema.json`. №4 импортирует его при сборке frontend. Отдельный `/api/rules/visualization` не нужен и не существует. Наличие ресурса не означает доступности DEPTH на сервере.

`generate_depth_fixtures.py` создаёт ресурс из каталогов; `check_repository.py` проверяет расхождения. Ручное редактирование производного ресурса не допускается. Неизвестные размеры не заменяются молча типовыми.

3D использует метрическую систему с локальным началом, например `[x-x0,y-y0,-h]`; увеличение вертикального масштаба явно подписано. GeoJSON остаётся двумерным, глубины — в свойствах. 2D с null не показывается как рассчитанная труба на 3 м. Для профиля выбранного пути нужны все рёбра этого пути; неполная загрузка страниц обозначается явно.
