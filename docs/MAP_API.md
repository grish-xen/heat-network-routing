# API карты

`GET /api/jobs/{jobId}/map` возвращает GeoJSON FeatureCollection с полями `features` и `nextCursor`. Данные доступны после `SUCCEEDED / DONE`; построение карты входит в этап EXPORTING.

```text
/api/jobs/<jobId>/map?layer=input&bbox=37.4,55.6,37.5,55.7&limit=1000
/api/jobs/<jobId>/map?layer=result&variantId=variant-1&bbox=37.4,55.6,37.5,55.7&limit=1000
```

Границы выше — пример запроса; клиент передаёт текущие границы экрана карты. Production-код не содержит координат конкурсного набора.

## Параметры

| Параметр | Значение |
| --- | --- |
| layer | Обязательный: input — исходные объекты, result — рассчитанные объекты одного варианта |
| bbox | Обязательный: minLon,minLat,maxLon,maxLat, WGS 84. Конечные числа, долгота −180…180, широта −90…90; минимум строго меньше максимума |
| variantId | Обязателен для result; берётся из `/variants`. Для input не передаётся |
| limit | Целое число 1…5000; по умолчанию 1000 |
| cursor | Значение nextCursor из предыдущего ответа; первый запрос без cursor |

Параметры нельзя повторять. Курсор привязан к задаче, слою, варианту, bbox и limit. После изменения области/варианта/размера страницы запрос начинается без cursor. Курсор непрозрачен для клиента; это не механизм авторизации.

Выборка выполняется по пересечению ограничивающих прямоугольников объектов с bbox, включая границу. Объекты возвращаются целиком, без обрезки по экрану. В результате возможны объекты, геометрия которых не пересекает bbox, но прямоугольник пересекает. Переход через антимеридиан одним bbox не поддерживается.

`result` не содержит `variant_summary` с null-геометрией: для них есть `/variants`. Типы и значения ID сохраняются, включая числовые ID за пределами точности JavaScript Number. Результирующие объекты берутся из того же GeoJSON, что скачивается через `/result`. Входные трёхмерные позиции преобразуются в двумерные удалением третьей координаты; долгота и широта сохраняются.

## Страницы и ошибки

Ответ имеет `Content-Type: application/geo+json` и `Cache-Control: no-store`. Страницы передаются потоком. Количество объектов не превышает limit; дополнительно действует предел 8 МиБ на страницу. Поэтому страница может быть короче limit даже при наличии продолжения. `nextCursor=null` означает конец выборки; отсутствие объектов возвращается как пустой features и null.

Если один объект не помещается в страницу с её оформлением, сервер отвечает 413 / MAP_FEATURE_TOO_LARGE. Геометрия не обрезается и не упрощается незаметно; полная геометрия остаётся в исходном файле либо скачиваемом результате. Уменьшение bbox не уменьшит размер целого объекта. Для таких объектов следующим улучшением будут упрощение геометрии или тайлы.

| HTTP | Код |
| --- | --- |
| 400 | INVALID_LAYER, INVALID_BBOX, INVALID_VARIANT, INVALID_LIMIT, INVALID_CURSOR, INVALID_MAP_QUERY |
| 404 | JOB_NOT_FOUND или VARIANT_NOT_FOUND |
| 409 | RESULT_NOT_READY — задача ещё не завершена успешно; MAP_DATA_UNAVAILABLE — у старой задачи нет архива карты либо он утрачен |
| 413 | MAP_FEATURE_TOO_LARGE |
| 500 | INTERNAL_ERROR при ошибке чтения |

Задачи, рассчитанные старой версией сервера без архива карты, сохраняют возможность скачать результат; для карты потребуется повторная загрузка исходного файла.

## Хранение

Перед удалением загрузки создаются четыре файла на задачу: `.map-input.data`, `.map-input.index`, `.map-result.data`, `.map-result.index`. Слой input строится из проверенного исходного GeoJSON, result — из законченного экспорта. Построение потоковое, без хранения всех геометрий в памяти. Рабочие файлы сначала имеют суффикс `.tmp`; задача получает SUCCEEDED после их публикации и закрытия Dataset.

Индекс содержит для каждого объекта границы в WGS 84, смещение и длину JSON-фрагмента, номер варианта. Запрос сканирует индекс блоками и читает только выбранные фрагменты из data. В памяти находятся не более 5000 описателей объектов страницы и небольшие буферы. Это последовательный дисковый индекс, а не R-tree; время запроса зависит от количества просмотренных записей.

Архивы сохраняются после перезапуска и удаляются вместе с задачей по сроку хранения. При ошибке расчёта/экспорта удаляются и опубликованные, и временные файлы карты. Сканирование и передача страницы не удерживают общую блокировку хранилища статусов. Открытые файловые дескрипторы закрываются и при обрыве HTTP-соединения. На Windows удаление используемого файла может быть повторено следующим проходом очистки.

Цена такого хранения — дополнительные дисковые копии геометрии входа и результата плюс индексы. Дисковые квоты, R-tree и нагрузочные испытания остаются отдельными задачами.

## Подключение интерфейса

Существующий `HttpHeatNetworkApi.getMapPage` использует этот контракт. Backend работает на 8080; Vite перенаправляет `/api`. Для реальных данных frontend запускается с `VITE_API_MODE=http`.

Frontend в этом PR не меняется. Его текущая реализация запрашивает все страницы области и собирает их в один массив; ограничение серверной страницы не ограничивает суммарную память браузера. Автоматическое приближение к загруженным данным, общий бюджет отображаемых объектов и проверка карты в браузере относятся к следующей совместной проверке с участником 4.

## Начальные границы без загрузки геометрии

`GET /api/jobs/{jobId}/map/bounds?variantId=<ID>` доступен после `SUCCEEDED / DONE`. Возвращает `application/json`, `Cache-Control: no-store`:

```json
{ "bbox": [37.4, 55.6, 37.5, 55.7] }
```

Числа в примере условные. Границы — точное объединение всех объектов input и геометрий только выбранного варианта result в WGS 84. Без геометрии, страниц и чтения исходного GeoJSON. Сервер сканирует фиксированные записи двух индексов блоками: память ограничена, время линейно числу записей. Работает и для ранее сохранённых архивов текущего формата.

Обязателен ровно один непустой variantId из `/variants`; другие параметры, включая bbox, layer, cursor и limit, не принимаются. Ошибки: 400 INVALID_VARIANT при отсутствии/пустом ID; 400 INVALID_MAP_QUERY при повторе или лишнем параметре; 404 JOB_NOT_FOUND / VARIANT_NOT_FOUND; 409 RESULT_NOT_READY / MAP_DATA_UNAVAILABLE; 500 INTERNAL_ERROR при ошибке чтения.

При отсутствии геометрий в обоих слоях возвращается `{ "bbox": null }` (200); не вызывайте fitBounds. Для точки или линии координаты границ могут совпадать: сервер не расширяет их искусственно. Используйте padding и maxZoom для fitBounds, а для `/map` берите реальные границы экрана после позиционирования — этот endpoint требует ненулевую ширину и высоту bbox. Через антимеридиан строится обычный min/max-прямоугольник без специального сокращения.

Вызывайте fitBounds один раз при первоначальном показе готовой задачи; повторная загрузка страниц не должна сбрасывать ручное перемещение карты. Автопозиционирование при смене варианта — решение интерфейса.
