# Чтение GeoJSON в Dataset

Реализован модуль участника 1: `GeoJsonInputParser` реализует согласованный `InputParser`. В Spring он доступен как bean. Участники 2 и 3 по-прежнему работают через `Dataset`; HTTP-загрузка и координация задач будут добавлены отдельно.

## Использование

```java
InputParser parser = new GeoJsonInputParser(Path.of("tmp", "datasets"));
try (Dataset data = parser.parse(Path.of("input.geojson"))) {
    try (Stream<Model.InputObject> objects = data.objects(Model.InputType.OKS_CONNECTION_POINT)) {
        objects.forEach(point -> System.out.println(point.flowTph));
    }
    Optional<Model.InputObject> object = data.find(new ObjectId(TextNode.valueOf("object-id")));
    try (Stream<Model.InputObject> candidates = data.query(new Envelope(400000, 401000, 6170000, 6171000))) {
        // Геометрии и координаты прямоугольника — метры, EPSG:32637.
    }
}
```

Импорты: `java.nio.file.Path`, `java.util.Optional`, `java.util.stream.Stream`, `org.locationtech.jts.geom.Envelope`, `com.fasterxml.jackson.databind.node.TextNode`, `ru.hackathon.heatnetwork.input.*`, `ru.hackathon.heatnetwork.model.*`.

В Spring конструктор сервиса получает `InputParser` через dependency injection. Базовая папка задаётся параметром `heat-network.input.storage-directory`, по умолчанию — `heat-network-routing` внутри системной временной папки. Для каждого вызова создаётся отдельная случайная подпапка. Сервис можно использовать одновременно для разных задач.

## Что проверяется

- Корневой `FeatureCollection`, массив features, ровно один корректный source; лишний JSON после коллекции и дубли ключей JSON отклоняются.
- Обязательные свойства каждого типа, уникальность ID с учётом исходного JSON-типа. `1` и `1.0` обозначают одно число, строка `"1"` отличается. Большие и дробные числовые ID сохраняются без промежуточного double.
- Диаметр существующей линии — целое значение из общего каталога. Расход цели — число не меньше нуля; нулевой расход не запрещён приложением. Дополнительные свойства игнорируются; неизвестный строковый restriction_type сохраняется для дальнейшей обработки.
- Point, LineString, MultiLineString, Polygon и MultiPolygon в соответствии с типом объекта; структура координат, конечные числа, замкнутость колец, валидность полигонов и положительная длина линий. Некорректная геометрия не исправляется автоматически.
- Координаты читаются как longitude/latitude, преобразуются в EPSG:32637 посредством [Proj4J](https://github.com/locationtech/proj4j). Присвоение SRID происходит после настоящего преобразования. Третья координата позиции, если есть, не участвует в обязательном 2D-режиме и не интерпретируется как глубина.
- Поле crs может отсутствовать или быть null; поддерживаются имена EPSG:4326 и CRS84, включая URN из конкурсного файла. Явно другая CRS отклоняется.

Ошибки данных выдаются как `InvalidInputException` с кодами и привязкой к `features[index]` и исходному ID, когда он корректен. После первых 100 ошибок чтение прекращается. Проблемы чтения/записи файлов остаются `IOException`; отмена потока — `InterruptedIOException`. Это не результат «маршрут не найден».

## Временное хранилище и память

Коллекция не превращается в общий JSON-tree или список всех геометрий. Посторонние поля пропускаются при чтении; в памяти собирается одна геометрия и её обязательные свойства. Память зависит от размера **самой большой отдельной геометрии**, а не всего файла. Один объект с гигантским числом вершин всё ещё требует памяти для JTS; это не устранено потоковым чтением коллекции.

Подготовленные объекты записываются в `objects.bin` (метаданные и WKB); `ids.bin` содержит дисковую таблицу поиска ID. Это временные файлы задачи; метаданные задач хранятся в PostgreSQL ([JOB_API.md](JOB_API.md)). Импорт не хранит все ID и геометрии в памяти.

`objects(type)` читает объекты лениво в порядке входа. `find(id)` использует дисковый индекс ID. `query(bounds)` последовательно проверяет сохранённые ограничивающие прямоугольники и загружает геометрии только совпавших объектов; точное пересечение проверяет вызывающий код. Пространственный поиск сейчас O(N): для крупных наборов и большого числа запросов будет нужен пространственный индекс, но интерфейс Dataset при этом менять не нужно.

Каждый Stream необходимо закрывать, особенно после `findFirst`/`limit`. После полного обхода файловый курсор закрывается автоматически. `Dataset.close()` закрывает оставшиеся курсоры и удаляет свою подпапку. Исходный GeoJSON не меняется и не удаляется. Ошибка импорта и прерывание также очищают создаваемое хранилище. При аварийном завершении JVM без close могут остаться временные файлы; фоновую уборку реализует будущий менеджер задач.

## Проверки

Тесты находятся в `backend/src/test/java/ru/hackathon/heatnetwork/input/`. Проверяются конкурсный набор, точность проекции эталона, типы ID и атрибутов, полигоны с отверстиями, ошибки, выборки и очистка. Отдельная JVM с `-Xmx64m` читает файл более 80 МБ с 40 000 целями. Это проверяет обработку входа, превышающего размер heap, но не заменяет будущий прогон предельных 3 ГБ и одновременных 50 пользователей.

Запуск из корня: `mvn -f backend/pom.xml verify`. Docker build context теперь корень репозитория, поскольку тесты используют общие файлы `test-data/`; запуск через Compose остаётся прежним.
