# Интерфейс сервиса моделирования тепловых сетей

## Цель

Создать рабочий демонстрационный интерфейс для участника 4, который проводит пользователя через загрузку GeoJSON, асинхронную обработку, просмотр маршрутов на карте, сравнение вариантов и скачивание результата. Интерфейс должен честно отражать текущее состояние backend: загрузка и получение статуса уже работают, а варианты, карта и результат пока доступны только через согласованные тестовые данные.

Успех первого релиза означает, что команда может продемонстрировать полный пользовательский сценарий на fixture-адаптере, проверить реальную загрузку и диагностику на HTTP-адаптере и переключить planned-операции на backend без изменения экранов и компонентов.

## Основания и ограничения

- Точный HTTP-контракт задан в [`contracts/openapi.json`](../../../contracts/openapi.json).
- Правила работы команды и границы модуля определены в [`AGENTS.md`](../../../AGENTS.md) и [`docs/TEAM_WORKFLOW.md`](../../TEAM_WORKFLOW.md).
- Согласованные ответы для независимой frontend-разработки находятся в [`test-data/api`](../../../test-data/api), а ожидаемый рассчитанный GeoJSON — в [`test-data/synthetic/two-consumers/expected.geojson`](../../../test-data/synthetic/two-consumers/expected.geojson).
- Реальный backend сейчас реализует `/api/health`, `POST /api/jobs` и `GET /api/jobs/{jobId}`. Успешная валидация пока заканчивается `FAILED / PROCESSING_UNAVAILABLE`.
- `/api/jobs/{jobId}/variants`, `/result` и `/map` остаются planned.
- Координаты карты — WGS 84, EPSG:4326. Метрические JTS-объекты в браузер не передаются.
- ID входных объектов могут быть строками или JSON-числами, в том числе больше безопасного диапазона JavaScript Number. Их исходный JSON-тип и точность нельзя терять.
- Входной файл может достигать 3 ГиБ, результат — 500 МиБ. Большие наборы нельзя целиком загружать в память браузера для отображения карты.
- Frontend не рассчитывает ДУ, стоимость или score и не подменяет ошибки расчёта частичным успехом.

## Технологический стек

- React и TypeScript для компонентов и типизированной модели.
- Vite для разработки и production-сборки.
- MapLibre GL JS для интерактивной карты.
- TanStack Query для запросов, polling, кеша и отмены устаревших запросов.
- `lossless-json` для разбора ответов без повреждения больших числовых ID.
- Vitest, React Testing Library и MSW для модульных и интеграционных frontend-тестов.
- Обычный CSS с токенами дизайна и локальными классами. Тяжёлая библиотека компонентов в первом релизе не нужна.

Проект ориентирован на современные desktop-браузеры с WebGL2. Планшет получает базовую адаптивную компоновку. Отдельная мобильная версия не входит в первый релиз.

## Архитектура

```text
frontend/src/
├── app/                 # запуск, провайдеры и общая компоновка
├── features/
│   ├── job-upload/      # выбор файла и отправка
│   ├── job-status/      # polling, этапы и диагностика
│   ├── variants/        # выбор и сравнение вариантов
│   └── network-map/     # MapLibre, bbox-загрузка, слои и легенда
├── shared/
│   ├── api/             # интерфейс API и его реализации
│   ├── model/           # HTTP-типы и runtime-проверки
│   ├── lib/             # lossless JSON, форматирование, утилиты
│   └── ui/              # переиспользуемые элементы интерфейса
└── test/                # общая настройка тестов
```

Приложение остаётся одностраничным и не использует роутер в первом релизе. TanStack Query хранит серверное состояние. Локальное состояние React хранит выбранный файл, вариант, слой и состояние панелей. Redux не добавляется.

### Граница API

Компоненты используют только интерфейс `HeatNetworkApi`:

- `health()`;
- `createJob(file, mode)`;
- `getJob(jobId)`;
- `listVariants(jobId)`;
- `getMapPage(jobId, query)`;
- `getResultUrl(jobId)`.

Реализации:

1. `fixtureApi` читает согласованные данные репозитория и имитирует переходы `QUEUED → RUNNING → SUCCEEDED` с контролируемыми задержками.
2. `httpApi` выполняет запросы к backend по OpenAPI и использует относительные `/api` URL.

Режим задаётся `VITE_API_MODE=fixture|http`. По умолчанию локальная демонстрация использует fixture-режим, а production-сборка требует явного выбора. В fixture-режиме постоянно отображается метка «Демонстрационные данные». Автоматического молчаливого отката с HTTP на fixtures нет.

Vite dev server проксирует `/api` на локальный backend, поэтому изменение CORS в чужом модуле не требуется.

### Безопасная работа с ID

HTTP-адаптер получает тело JSON как текст и разбирает его через `lossless-json`. Runtime-преобразователь знает схему ответа:

- поля ID сохраняются как строковый или специальный точный числовой идентификатор;
- числовой идентификатор хранит исходное десятичное представление и не участвует в арифметике;
- координаты, стоимость, длина, расход и score преобразуются в обычные числа только после проверки допустимого диапазона;
- ключи React и MapLibre строятся из пары «JSON-тип + точное значение», поэтому число `1` и строка `"1"` не совпадают.

Тип `ObjectId` не раскрывает конкретную библиотеку компонентам. Форматирование и сравнение сосредоточены в `shared/model`.

## Пользовательский сценарий

### Начальное состояние

Пользователь видит назначение сервиса, допустимый формат и область загрузки. Можно выбрать или перетащить один `.geojson`/`.json` файл. Интерфейс не читает весь файл для предварительного разбора; проверяются только наличие, расширение и доступный браузеру размер.

### Отправка и обработка

После отправки приложение показывает ID задачи, режим `2d`, текущий этап и последовательность:

1. файл принят;
2. проверка данных;
3. поиск маршрутов;
4. инженерный расчёт;
5. подготовка результата.

HTTP polling выполняется примерно раз в секунду для `QUEUED` и `RUNNING` и прекращается для `SUCCEEDED` и `FAILED`. Успех определяется только сочетанием `SUCCEEDED / DONE`.

`PROCESSING_UNAVAILABLE` объясняется как успешно проверенный файл при ещё не подключённом расчёте. Интерфейс не показывает fixture-маршрут как результат этой реальной задачи.

### Результат

После успеха загружаются сводки вариантов и карта. Выбран вариант с минимальным rank. Пользователь может:

- сравнить до трёх вариантов;
- переключить вариант на карте;
- включать и выключать группы слоёв;
- открыть свойства объекта;
- приблизить карту к данным;
- скачать итоговый GeoJSON через обычную браузерную загрузку без предварительного чтения файла в JavaScript.

## Компоновка и визуальная система

Основной экран desktop-first:

- верхняя полоса содержит название, состояние API и метку режима данных;
- левая панель шириной около 360–420 px содержит загрузку, прогресс, ошибки и варианты;
- оставшееся пространство занимает карта;
- на узком планшетном экране панель становится выдвижной, карта остаётся основным контекстом.

Визуальный язык инженерный и спокойный: светлая нейтральная поверхность, тёмный текст, красно-оранжевый акцент новой тепловой сети. Существующая сеть, камеры, точки ОКС и ограничения получают отдельные контрастные обозначения. Цвет не является единственным носителем смысла: используются разные толщины линий, штрихи, формы маркеров и подписи легенды.

Карта показывает:

- `source`;
- существующий `heat_network`;
- существующие и новые `heat_chamber`;
- `oks_connection_point`;
- ограничения по `restriction_type`;
- рассчитанный `heat_network`;
- `technical_node`.

Popup отображает только пришедшие от API свойства и не выводит внутренние метрические или графовые ID.

## Загрузка карты

Карта запрашивает `MapPage` по bbox текущего viewport. Для `result` передаётся выбранный `variantId`. Один логический запрос следует по `nextCursor` с теми же bbox, layer, variantId и limit до `null`.

При изменении viewport предыдущая незавершённая цепочка отменяется. Результаты разных bbox и вариантов имеют разные query keys. На карту передаётся только текущая ограниченная страница/цепочка, а не исходный файл до 3 ГиБ.

Fixture-адаптер применяет тот же интерфейс, фильтрует fixture-геометрию по bbox и возвращает страницы, чтобы компоненты проверялись в том же режиме работы, что и будущий backend.

## Ошибки и восстановление

- Ошибки приёма `400`, `413`, `415`, `422` показываются рядом с формой и сохраняют выбранный файл для повторной попытки.
- `503` показывает заполненную очередь и учитывает `Retry-After`, но повторная отправка остаётся явным действием пользователя.
- `404` статуса объясняет истечение срока хранения или неизвестную задачу и предлагает начать заново.
- Асинхронные `diagnostics` отображаются списком с кодом, сообщением и безопасными ссылками на объект.
- Сетевой сбой polling не превращает задачу в `FAILED`: показывается временная потеря связи и кнопка повторить запрос.
- Отсутствие WebGL2 даёт отдельное состояние с сохранением доступных сводок вариантов.
- Некорректный ответ API считается интеграционной ошибкой; UI не пытается угадать отсутствующие обязательные поля.

## Доступность

- Все действия доступны с клавиатуры и имеют видимый focus.
- Зона загрузки использует настоящий `input type=file` и связанную подпись.
- Прогресс объявляется через `aria-live` без постоянного повторения сообщений polling.
- Карточки вариантов реализуются как доступная группа выбора.
- Значения не передаются только цветом; числа имеют текстовые подписи и единицы.
- Уважение `prefers-reduced-motion` отключает необязательные переходы карты и интерфейса.

## Проверки

### Модульные

- сохранение строковых и больших числовых ID без коллизий;
- форматирование рублей, метров, т/ч и score;
- runtime-проверка Job, Error, VariantSummary и MapPage;
- преобразование bbox и query parameters;
- фильтрация fixture-карты.

### Компонентные

- выбор файла и отправка multipart без ручного заголовка `Content-Type`;
- polling до терминального состояния и его остановка;
- отображение `PROCESSING_UNAVAILABLE` и входных диагностик;
- выбор и сравнение вариантов;
- переключение слоёв и обработка отсутствия WebGL.

### Интеграционные

- полный fixture-сценарий от загрузки до карты;
- HTTP-сценарий с MSW для 202, polling, ошибок и planned-операций;
- production-сборка TypeScript/Vite.

Реальный backend проверяется отдельно: frontend-тесты не выдают fixture-ответы за серверные.

## Интеграция и поставка

- `npm ci`, `npm test` и `npm run build` добавляются в GitHub Actions отдельным frontend-шагом/job без изменения backend-проверок.
- В [`frontend/README.md`](../../../frontend/README.md) документируются Node-версия, команды, режимы API и dev-proxy.
- Docker-интеграция не входит в первый frontend-инкремент: сначала команда получает проверяемую статическую сборку. Подключение раздачи frontend согласуется с участником 1 отдельным небольшим PR.
- Изменение `contracts/openapi.json` не требуется. Если фактический backend разойдётся с контрактом, frontend фиксирует интеграционную ошибку, а изменение контракта выполняется согласованно.

## Коммиты и взаимодействие с командой

Работа делится на небольшие коммиты, каждый из которых собирается и имеет понятное сообщение:

1. спецификация интерфейса;
2. каркас React/Vite и тестовая среда;
3. типы, lossless JSON и два API-адаптера;
4. загрузка, polling и диагностика;
5. карта и bbox-пагинация;
6. варианты, сравнение и скачивание;
7. CI, документация и финальная интеграционная проверка.

Перед началом очередного инкремента ветка синхронизируется с `origin/main` обычным merge без force push. Общие контракты не меняются внутри frontend-коммита.

## Не входит в первый релиз

- инженерные расчёты в браузере;
- редактирование геометрии и ручная корректировка маршрута;
- режим глубины;
- полноценная мобильная компоновка;
- авторизация и управление пользователями;
- хранение истории задач дольше серверного срока;
- собственный тайловый сервер или офлайн-карты;
- изменение backend API, Docker Compose или общей модели без согласования.
