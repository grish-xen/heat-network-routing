# Depth UI and 3D scene Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver an attractive, interactive 3D depth view and a longitudinal profile for calculated DEPTH results, without weakening existing 2D or HTTP behavior.

**Architecture:** Keep parsing and graph/path construction as pure TypeScript modules. `DepthScene` owns an imperative Three.js canvas adapter, matching the existing MapLibre adapter pattern; it consumes metric scene data only. `ResultWorkspace` owns selected view and endpoint state, while fixture mode explicitly supplies the agreed DEPTH response files.

**Tech Stack:** React 19, TypeScript, TanStack Query, Three.js with OrbitControls, proj4, SVG, Vitest, Testing Library.

**Spec:** `docs/superpowers/specs/2026-09-28-depth-ui-3d.md`

## Global Constraints

- Import `contracts/visualization-rules.v1.json` at build time; never fetch it from `/api`.
- Transform WGS84 into local metric scene coordinates before rendering; scene elevation is `-depth × 4`.
- Preserve `422 UNSUPPORTED_MODE` in HTTP mode and never replace it with fixtures.
- Use all map pages and existing cancellation-aware query helpers.
- Keep map/profile available if WebGL cannot start; do not invent terrain or building heights.
- Write a failing focused test before each production change and run the full frontend suite before task completion.

## Review Focus

- A depth feature with a numeric ID greater than `Number.MAX_SAFE_INTEGER` retains the ID losslessly in graph/path selection.
- A 2D result containing no depth fields cannot accidentally activate the 3D scene.
- A DEPTH request in HTTP mode still exposes the server's 422 message instead of demo data.
- A branched result never joins unrelated edges into one route; the selected endpoint determines a connected source-to-endpoint path.
- A WebGL initialization failure leaves the map and profile navigable.

## Self-review

- Spec coverage: Tasks 1–2 cover contracts and mode behavior; Task 3 covers metric conversion, paths and profile; Task 4 covers real 3D interaction and fallback; Task 5 covers workspace UX and responsive presentation; Task 6 covers project and browser verification.
- Type consistency: the parser supplies `MapFeatureProperties`; `buildDepthPaths` consumes those properties; profile and scene consume its output; the workspace owns the selected path.
- Review focus: large IDs (Task 1/3), missing depth (Task 3/5), HTTP 422 (Task 2), branches (Task 3/5), and WebGL failure (Task 4/5) are each assigned a test.
- Proportion: the implementation is split by independently testable data, API, renderer and workspace boundaries; no backend scope is included.
