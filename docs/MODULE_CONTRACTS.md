# Контракты модулей — версия 1.0

Сигнатуры уже находятся в Java и проверяются общей сборкой. Реализации должны реализовать эти интерфейсы, а не создавать альтернативные типы с тем же смыслом.

| Интерфейс | Вход → выход | Владелец |
| --- | --- | --- |
| `input.InputParser` | Путь к файлу → `Dataset`; ошибки входа → `InvalidInputException` с диагностикой | 1 |
| `routing.RoutePlanner` | Dataset + SearchOptions → SearchSession | 2 |
| `routing.SpatialValidator` | Dataset + окончательный CalculatedVariant → нарушения геометрии/топологии | 2 |
| `calculation.VariantCalculator` | Dataset + RouteCandidate + Mode → Evaluation | 3 |
| `output.ResultExporter` | Dataset + до трёх рассчитанных вариантов одного режима, уже отсортированных → поток GeoJSON | 1 |
| HTTP API | Загрузка, статусы, варианты, карта, скачивание по `contracts/openapi.json` | 1 и 4 |

`InputParser` реализован классом `GeoJsonInputParser`; возвращается временный дисковый Dataset. Интеграция — [INPUT_MODULE.md](INPUT_MODULE.md). `ResultExporter` реализован классом `GeoJsonResultExporter` для 2D — [OUTPUT_MODULE.md](OUTPUT_MODULE.md). `VariantCalculator` реализован классом `DefaultVariantCalculator` для 2D — [CALCULATION_MODULE.md](CALCULATION_MODULE.md). Маршрутизатор и пространственные проверки — `GridRoutePlanner` и `DefaultSpatialValidator`. Общий контракт 1.0 не менялся; в каталог добавлен справочный `profileWidthM` для газопровода и кабеля.

## Общий запуск

Координатор участника 1 хранит задачу, получает Dataset и открывает SearchSession. Он вызывает `next()`, оценивает кандидата через VariantCalculator, передаёт `feedback(evaluation)` в ту же сессию и продолжает поиск. Пустой Optional означает окончание поиска в выделенном бюджете; это не доказательство технической невозможности подключения.

VariantCalculator считает расход, выбирает ДУ с учётом длины и монотонности, выделяет специальные проходы/технические узлы и вычисляет цену. После формирования окончательной геометрии он вызывает SpatialValidator. Положительный Evaluation возможен только после обязательных расчётных и пространственных проверок. `variant == null` означает отклонение; `diagnostics` объясняет причину.

Владелец трассировки также использует пространственные проверки во время поиска. Поиск должен уметь получить отклонение после увеличения ДУ и предложить другой вариант: нужная ширина трассы заранее неизвестна. Финальные проверки нельзя заменять успешностью предварительного маршрута.

Координатор сохраняет содержательно разные допустимые варианты, выбирает до трёх с минимальным score и передаёт их экспортёру по порядку. Формулу стоимости/score реализует участник 3; API и frontend повторно её не вычисляют. Все потоки и сессии закрываются. Отмена/сбой освобождает временные ресурсы.

Экспортёр получает Dataset для проверки ссылок и коллизий новых ID с исходными. Dataset закрывается после завершения экспорта; сам экспортёр не закрывает переданный OutputStream, это обязанность вызывающего.

Экспортёр не присваивает внутренним узлам новые ID на месте: сопоставление со строковыми выходными ID действует только внутри конкретной записи файла. Исходные ID остаются числами/строками. Некорректный рассчитанный результат даёт `InvalidResultException`, превышение 500 МиБ — `OutputLimitExceededException` (оба IOException). Частично записанный файл не публикуется. Координатор расчёта и экспорта подключён к API задач; частичные файлы недоступны по HTTP.

## Ошибки

Общие диагностические коды: `INVALID_INPUT`, `INVALID_ID`, `INVALID_GEOMETRY`, `TOPOLOGY_VIOLATION`, `CLEARANCE_VIOLATION`, `TURN_VIOLATION`, `SPECIAL_PASS_VIOLATION`, `DIAMETER_LIMIT`, `LENGTH_LIMIT`, `ROUTE_NOT_FOUND`, `UNSUPPORTED_MODE`, `INTERNAL_ERROR`. Поле message — понятное пояснение, ссылки на исходный объект/участок добавляются, если известны.

Нарушение кандидата даёт Evaluation с причинами. Ошибка входных данных прекращает задачу с диагностикой. Внутренний сбой не превращается в успешный результат с неподключёнными точками. Частичное подключение — допустимый успешный результат со списком точек и штрафом, если для них не найден маршрут.

`SearchOptions.maxCandidates` и `seed` — командные параметры поиска, не ограничения организатора. `DEPTH` зарезервирован контрактом; пока режима нет, возвращать `UNSUPPORTED_MODE`, а не результат 2D под другим названием.

## Проверяемый пример

`test-data/synthetic/two-consumers/metric-case.json` — форма записи примера для людей/тестов: `xy` преобразуется в JTS, SRID = 32637. Это не второй production DTO. В рёбрах записаны ожидаемые расчётные поля: RouteCandidate берёт ID, связи и xy, а участник 3 проверяет свой результат по остальным значениям. `input.geojson` и `expected.geojson` — согласованные с ним данные в WGS 84.

## HTTP-контракт

Полный документ: `contracts/openapi.json`. Реализованы `/api/health`, POST `/api/jobs`, GET `/api/jobs/{jobId}`, GET `/api/jobs/{jobId}/variants`, GET `/api/jobs/{jobId}/result` и GET `/api/jobs/{jobId}/map`. Публичный Swagger документирует эти операции. Правила страниц карты — [MAP_API.md](MAP_API.md). Поведение, очередь, хранение и подключение координатора описаны в [JOB_API.md](JOB_API.md).

Фоновая обработка проходит полную цепочку. SUCCEEDED/DONE появляется после сохранения результата и сводок. Ошибочный вход заканчивается диагностикой InputParser; отсутствие принятого варианта — ROUTE_NOT_FOUND, превышение размера экспорта — OUTPUT_LIMIT_EXCEEDED. Ошибки перезапуска: SERVER_RESTARTED, JOB_INTERRUPTED и RESULT_UNAVAILABLE при утрате сохранённого результата; HTTP-коды приведены в OpenAPI. Структуры Job/Error не изменены; уточнены Location, Cache-Control, Retry-After и ответы 415/500.

POST `/api/jobs` сохраняет multipart-файл и отвечает 202; валидация и расчёт продолжаются асинхронно. GET `/api/jobs/{jobId}` отдаёт статус. GET `/api/jobs/{jobId}/variants` отдаёт сводки с официальными snake_case полями. GET `/api/jobs/{jobId}/result` скачивает GeoJSON потоком. GET `/api/jobs/{jobId}/map` возвращает страницу пространственных объектов по bbox, слою и варианту. Архив карты сохраняется после закрытия Dataset. Страница ограничена числом объектов и 8 МиБ; frontend отдельно должен контролировать суммарный объём загруженных страниц.

Во время реализации каждая операция отмечается implemented в спецификации и покрывается проверкой фактического ответа. Новые общие поля/изменение семантики — через PR с обновлением модели, контрактов, примеров и затронутых вызовов.

Координатор исключает промежуточный частичный вариант, если найден допустимый вариант, подключающий все его точки и дополнительные. Остальные варианты ранжируются по score и дедуплицируются без служебных ID. В HTTP выдаётся до трёх вариантов; публичные ID variant-1 … variant-3 относятся к задаче. Сводки читаются из готового экспорта, поэтому суммы и ID совпадают с файлом. Подробности жизненного цикла — JOB_API.md.

## Начальная область карты (модули 1 и 4)

GET `/api/jobs/{jobId}/map/bounds?variantId=<ID>` после SUCCEEDED / DONE возвращает `MapBounds` — границы input + выбранного результата. variantId обязателен, берётся из `/variants`. Модуль 1 читает только дисковые индексы, модуль 4 вызывает fitBounds и затем `/map` для видимой области. Пустая карта: bbox=null. Для точки/линии frontend задаёт maxZoom; фиксированные стартовые координаты не заменяют границы данных. Полная семантика и ошибки — [MAP_API.md](MAP_API.md).
