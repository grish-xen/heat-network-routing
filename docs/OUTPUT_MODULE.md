# Модуль экспорта результата

Обновление: экспорт поддерживает готовые варианты TWO_D и DEPTH. В одном файле допускается только один режим. HTTP-задачи DEPTH подключены после сквозной интеграции — [DEPTH_INTEGRATION.md](DEPTH_INTEGRATION.md).

`output.GeoJsonResultExporter` реализует существующий `ResultExporter` и зарегистрирован как Spring bean. На вход подаются открытый Dataset и от одного до трёх **уже проверенных и рассчитанных** `CalculatedVariant`, отсортированных по возрастанию score. На выходе — один потоковый GeoJSON FeatureCollection в WGS 84.

Сигнатура контракта 1.0 и типы `model.Model` сохранены. Формат организаторов описан в [OUTPUT_FORMAT.md](OUTPUT_FORMAT.md). Экспортёр пишет только новые участки, новые камеры, технические узлы и сводки. Существующие камеры и точки подключения остаются внешними ссылками на входной файл.

## Подключение участником 1

Внедрите `ResultExporter` в координатор через конструктор. После выбора рассчитанных вариантов:

```java
// dataset принадлежит координатору и остаётся открытым на время экспорта.
// rankedVariants уже прошли VariantCalculator и SpatialValidator.
try (OutputStream stream = Files.newOutputStream(temporaryResult)) {
    exporter.write(dataset, rankedVariants, stream);
}
// Только после успешного закрытия файла публикуйте результат задачи.
// При исключении удалите temporaryResult; такой файл не является результатом.
```

Для этого фрагмента нужны `java.io.OutputStream`, `java.nio.file.Files` и обычные локальные переменные координатора. Экспортёр сам не создаёт HTTP-задачу, не выбирает варианты и не ставит `SUCCEEDED`. Координатор закрывает Dataset после последнего потребителя. Переданный OutputStream экспортёр не закрывает ни при успехе, ни при ошибке.

API задач вызывает экспортёр после отбора вариантов. Результат сначала сохраняется во временный файл, затем из него извлекаются сводки. После публикации файлов и закрытия Dataset задача получает SUCCEEDED. Скачивание, варианты и карта реализованы; карта результата строится из этого же экспорта. См. [JOB_API.md](JOB_API.md).

## Координаты и поля

- Внутренние Point/LineString должны иметь SRID 32637. Proj4J выполняет обратное преобразование UTM 37N → WGS 84; простая смена SRID не применяется.
- В GeoJSON порядок координат — долгота, широта. Геометрия пишется по одной позиции, без копии всей линии в массиве JSON. Z не экспортируется в обоих режимах. В TWO_D глубины null, в DEPTH — числовые значения depthStartM/depthEndM рассчитанного участка, без подстановки или округления экспортёром.
- `length`, расход, ДУ, цены и score берутся из рассчитанного варианта. Экспортёр не выбирает ДУ, не применяет тарифы и не вычисляет score заново.
- Концы линии проверяются относительно указанных узлов с допуском 1 мм в метрах. При расхождении в пределах допуска в файл записывается координата узла, а для исходной точки/камеры — её координата из Dataset. Проверяется длина до и после этого согласования. Входные DTO/JTS-геометрии не изменяются.
- Внутренние вершины LineString сохраняются; обычный поворот не порождает technical_node.
- `rank` равен позиции в переданном списке, начиная с 1. Равные score допустимы; порядок сохраняется. `variant_id` сохраняется из `CalculatedVariant.variantId`.

## Идентификаторы

Для каждого нового выходного объекта создаётся строковый ID вида `hnr-1`, `hnr-2`, … в общем счётчике одного файла. Каждый кандидат проверяется через `Dataset.find`; совпадающий с входным ID пропускается. Счётчик не переиспользуется между вариантами. В память не загружается набор всех исходных ID.

Эти выходные ID непрозрачны для потребителей: не вычисляйте их по внутренним именам узлов/рёбер. Порядок распределения может отличаться от порядка features. Связи `start_node_id` / `end_node_id` записываются через таблицу соответствия узлов; ID исходных точек и камер сохраняют числовой либо строковый JSON-тип и точность. Это также относится к `unconnected_oks_ids`.

Эталон `test-data/synthetic/two-consumers/expected.geojson` остаётся прежним: он задаёт геометрию и свойства, а имена новых ID в нём иллюстративные. Проверка экспортёра сопоставляет эти ID и сравнивает остальные поля и координаты с эталоном.

## Проверки перед записью

Все варианты проходят структурные проверки до первого байта результата:

- 1–3 варианта с уникальными непустыми variantId; один непустой режим TWO_D либо DEPTH; порядок по score.
- Уникальные внутренние ID узлов и рёбер, обязательные свойства, конечные координаты и правильный SRID.
- Существующие ссылки ведут на входную камеру либо точку подключения соответствующего типа; концы линий совпадают с узлами.
- Новые камеры имеют ровно одну запись стоимости; существующие камеры не выдаются за новые. Нет узлов, не используемых участками.
- Каждая входная точка представлена как подключённая либо как неподключённая, без пересечения этих списков и повторов.
- Длины соответствуют геометрии; суммы участков/камер и сводки согласованы. Неотрицательные числа не заменяются нулями при пропуске поля.
- DEPTH: обе глубины конечны и не ниже минимума из depth-v1.json, перепад не превышает максимальный уклон по горизонтальной длине, участок разделён при переходе через порог Kгл. Глубины верха в общих узлах согласованы с допуском 1e−6 м по depth-contract-1. Проверяется размах всех значений узла, поэтому цепочка малых отклонений не скрывает разрыв. Глубины не исправляются автоматически.

`DepthExportValidation` читает минимальную глубину, уклон и порог Kгл из общего дополнения каталога; верхнего ограничения глубины не добавляет. Уклон допускает только погрешность double на точной границе, ограниченную 1e−9 м перепада. Стоимость, вертикальные просветы, политика глубин корня/потребителя и форма спецпроходов остаются ответственностью калькулятора и пространственного валидатора. Положительный экспорт не доказывает инженерную допустимость произвольного графа.

Это проверки согласованности выгружаемых данных. Инженерные ограничения, препятствия, допустимость ветвлений, обоснованность неподключения, применимость тарифа и содержательное различие вариантов проверяют `VariantCalculator` и `SpatialValidator` до вызова экспортёра. `attachments` не является выходным объектом и не сериализуется; его топологическую корректность проверяют эти модули.

## Ошибки, память и размер

- `InvalidResultException extends IOException` — нарушение контракта рассчитанного результата. Это ошибка внутреннего расчёта/интеграции; её нельзя выдавать пользователю как ошибку загруженного GeoJSON.
- `OutputLimitExceededException extends IOException` — превышен предел **524 288 000 байт (500 МиБ)**. Считаются байты UTF-8, включая свойства и координаты.
- `InterruptedIOException` — отмена через прерывание потока; флаг прерывания сохраняется. Ошибки Dataset/выходного потока передаются вызывающему коду.
- Превышение размера, отмена или ошибка записи могут оставить неполный файл. Координатор должен записывать в служебный файл и публиковать его только после полного успеха.

Экспортёр не создаёт полный JSON-документ, строку или копию массива координат в памяти. Дополнительная память нужна для таблиц узлов, проверяемых ID и ссылок; она растёт с числом объектов графа. Сам `CalculatedVariant` уже находится в памяти у вызывающего кода. Это не обещание постоянного потребления памяти для любого графа.

Проверено:

- Все семь общих DEPTH-примеров: глубины, типы ссылок, сводки и двумерная геометрия, без изменения переданного графа. Некорректные глубины и смешение режимов отвергаются до первого байта. Настоящий экспорт проходит через FileJobStore и многостраничный MapArchive с сохранением после перезапуска; отсутствующий профиль не публикуется. Эти тесты подают готовый профиль, а не выполняют DEPTH solver.

- Эталон с двумя потребителями через настоящий GeoJSON InputParser; точные типы ID, координаты, поля сводки и внешние ссылки.
- Три варианта, коллизии ID, технические узлы, специальные участки, обычные повороты, неподключённые точки, ошибки данных и одновременные вызовы одного Spring-компонента.
- Граница байтового лимита проверена с уменьшенным порогом; полная запись файла 500 МиБ не выполнялась.
- Отдельная JVM с `-Xmx64m` записывает и затем потоково читает файл **76 841 002 байта**: одна линия из 2 000 000 позиций. Доступный heap — 67 108 864 байта. Проверка входит в Maven verify и CI; это проверка экспорта, а не скорости маршрутизации или 50 одновременных пользователей.
