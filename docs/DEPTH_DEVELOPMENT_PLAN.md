## 1. Результат этапа

Пользователь выбирает «2D» или «С учётом глубины», загружает тот же GeoJSON и получает отдельную задачу. В режиме глубины результат содержит допустимый вертикальный профиль, стоимость с учётом глубины, карту и скачиваемый GeoJSON. Для выбранной трассы доступны продольный профиль и 3D-сцена.

Расчёт глубины и переключение отображения — разные действия. Переключение «карта / профиль / 3D» показывает один рассчитанный результат и не запускает новый расчёт. Для смены расчётного режима создаётся новая задача. Варианты 2D и DEPTH не попадают в общий рейтинг.

Первый рабочий результат: небольшая сеть пересекает газопровод, получает допустимый подъём или заглубление и возврат; глубины, стоимость и отображение согласованы. Затем — несколько препятствий и разветвлённая сеть.

### Текущее состояние

- Ветка исправления `fix/routing-search-runtime`, коммит `187c12d`, PR #16: 17/17 подключений на конкурсном наборе, 181 тест, успешные HTTP-проверки и CI. Подробности — [отчёт](ROUTING_RUNTIME_CHECK.md).

## 2. Правила организатора

| Вопрос | Требование |
| --- | --- |
| Поверхность | Условная горизонтальная поверхность земли |
| Значение глубины | Метры до **верхней границы расчётного габарита** новой сети, положительное направление вниз |
| Обычная / минимальная глубина | 3,0 м / 0,7 м |
| Уклон | Не более 0,10 м/м; изменение на 1 м требует минимум 10 м горизонтальной длины |
| Максимальная глубина / шаг | Организатором не заданы; выбранный поисковый предел нельзя выдавать за норматив |
| Длина для стоимости и ограничений | Длина горизонтальной проекции в EPSG:32637 |
| Геометрия экспорта | WGS 84, двумерные координаты допустимы; глубины задаются `depth_start`, `depth_end` |
| Коэффициент глубины | `K(h)=1` при `h<=3`; иначе `1+0.10*(h-3)` |
| Стоимость наклонного участка | Среднее коэффициентов начала и конца; при переходе через 3 м обязательно разделение техническим узлом |
| Специальные проходы | Плановые требования сохраняются; на пересечениях дополнительно проверяются вертикальные расстояния |
| Запретные территории | Уход на глубину не даёт разрешения пересечь запрещённый объект |
| Изменение профиля | Спуск/подъём, постоянная глубина, при необходимости возврат; между близкими препятствиями можно сохранять изменённую глубину |

| Пересекаемый объект | Условное положение объекта | Требование к новой сети |
| --- | --- | --- |
| Дорога | Полигон на поверхности | Верх габарита не выше глубины 1,0 м |
| Трамвайные пути | Полигон на поверхности | Верх габарита не выше глубины 1,2 м |
| Газопровод | Верх 2,8 м, габарит 0,40 × 0,40 м | Выше или ниже; просвет минимум 0,2 м |
| Силовой кабель | Верх 2,7 м, габарит 0,20 × 0,20 м | Выше или ниже; просвет минимум 0,5 м |
| Существующая теплосеть без врезки | Верх 3,0 м, габарит по ДУ из таблицы 1 | Выше или ниже; просвет минимум 0,5 м |

Все числа хранятся в общем каталоге после его расширения. Frontend получает необходимые размеры из подготовленного участником 1 представления каталога. Копировать числа вручную в несколько модулей нельзя.

## 3. Как модули будут работать вместе

Предлагаемая архитектура сохраняет существующие внешние Java-интерфейсы:

```text
Участник 1: загрузка → Dataset → SearchOptions(mode=DEPTH)
Участник 2: RoutePlanner → плановый RouteCandidate
Участник 3: расходы → ДУ → специальные интервалы → профиль глубины
            → деление конечных участков → стоимость
Участник 2: SpatialValidator проверяет окончательный CalculatedVariant
Участник 3: Evaluation: допустимый вариант либо причины отказа
Участник 1: feedback маршрутизатору → отбор → экспорт → API
Участник 4: карта / профиль / 3D по данным API
```

**Владелец построения профиля — участник 3.** Ему уже известны расходы, ДУ, габариты и специальные интервалы. Участник 2 строит плановые альтернативы и независимо проверяет окончательный профиль. При невозможности профиля кандидат отклоняется через Evaluation; SearchSession получает feedback и продолжает искать другой допустимый маршрут.

Предлагаемый внутренний класс `calculation.DepthProfilePlanner` создаётся внутри модуля 3. Его DTO не становятся вторым общим контрактом. Пространственный валидатор проверяет конечные глубины самостоятельно; вызов того же построителя вместо проверки не считается независимой валидацией.

### Порядок расчёта у участника 3

1. Проверить граф, посчитать расходы, подобрать ДУ с учётом непрерывных путей и горизонтальных длин.
2. Определить специальные интервалы и их наложения, используя окончательные габариты.
3. Получить допустимые вертикальные интервалы: проход выше либо ниже коммуникации, минимальная глубина, условия дороги/трамвая.
4. Подобрать непрерывный профиль с уклоном не более 0,10. Учитывать общие камеры и ветви совместно, а не независимо для каждого ребра.
5. Объединить места деления: границы спецпроходов, смена уклона, пересечение глубины 3 м и существующие узлы. Не создавать совпадающие технические узлы; они не дают права на ветвление и не имеют отдельной стоимости.
6. Рассчитать стоимость всех конечных частей, камер и врезок; вызвать SpatialValidator.
7. При отклонении вернуть понятную диагностику. Неподключение нельзя использовать для искусственного улучшения score.

Первый алгоритм может начинать с обычной глубины 3 м и рассматривать положения выше/ниже препятствий, заданные границами допустимых интервалов. Это стратегия поиска команды, а не требование фиксированного шага глубины. Для близких препятствий нужно проверять комбинации и возможность сохранять изменённую глубину; независимый выбор самого дешёвого прохода на каждом пересечении недостаточен.

### Вопросы, которые нужно закрыть в D1

В проверенных разделах ТЗ недостаточно подробно определены следующие стыки. Участник 1 с участниками 2 и 3 фиксирует принятые допущения, а при необходимости готовит вопрос организаторам. Отправка вопросов — отдельное действие команды.

1. **Глубина врезки и подключения к ОКС.** Предложение для первого режима: верх на 3 м в корневой точке и у потребителя. У входных точек нет собственной глубины; это допущение, которое может влиять на достижимость маршрута.
2. **Стыки разных ДУ в камере.** Что должно совпадать: верх габарита или ось? Предложение: одинаковая глубина верха у примыкающих новых участков; высота каждого габарита определяется своим ДУ. Нельзя вводить это молча как норматив организатора.
3. **Вертикальная форма спецпрохода.** Предложение: постоянная глубина внутри требуемой протяжённости прохода, подъём/спуск снаружи. Это консервативное толкование прямого спецпрохода; проверить согласованность с ТЗ до реализации.
4. **Пересечение двух новых трасс в плане.** В первом режиме сохранять запрет пересечения вне общего узла даже при разных глубинах. Разрешение таких пересечений потребует отдельных правил и проверки; это ограничение выбранного поиска.
5. **Размеры для интерфейса.** Выбрать и описать один способ доставки каталога: отдельный ограниченный HTTP-ответ (предлагаемое имя `GET /api/rules/visualization`) либо автоматически создаваемый из каталога ресурс сборки. Зафиксировать схему и версию; до этого №4 использует только согласованные тестовые данные. Endpoint пока не существует.

### Минимальные общие примеры

Участник 1 заводит `test-data/synthetic/depth/` и `test-data/api/depth/` в D1. Каждый пример содержит вход, метрическое описание для тестов, ожидаемые допустимые границы и результат/диагностику. Ожидания проверяют правила; единственный конкретный маршрут не обязателен, если допустимых несколько.

Пример полей **одного уже разделённого** участка (эскиз свойств, не полный GeoJSON):

```json
{ "depth_start": 3.0, "depth_end": 3.4, "length": 4.0, "laying_method": "base" }
```

Уклон здесь 0,10; средний Kгл = 1,02. Стоимость части равна `4 * ставка_ДУ * 1.02`. Для участка от 2 до 4 м за 20 м сначала делим на отметке 3 м: 10 м с K=1 и 10 м со средним K=1,05. Усреднение только исходных концов дало бы неправильную стоимость.

Для газопровода с верхом 2,8 м и высотой 0,4 м проход ниже требует `h_new >= 3.4`; проход выше требует `h_new + H_new <= 2.6`. Это расстояния между габаритами. Проверка только расстояния между осями неверна.

### D4. Сложные профили и визуализация — параллельно

Участники 2–3: близкие и наложенные препятствия, несколько ветвей, несовместимые интервалы, смена ДУ, обратная связь и альтернативные маршруты. Проверить сохранение увеличенной глубины вместо ненужного подъёма и повторного спуска.

Участник 4: сначала продольный профиль «горизонтальное расстояние — глубина», затем отдельная 3D-сцена выбранного пути. Для ветвящейся сети пользователь выбирает потребителя и путь от присоединения; нельзя рисовать все рёбра подряд как одну линию.

Для первой 3D-версии нужны вращение/масштабирование, условная поверхность, расчётные габариты труб и пересекаемых коммуникаций, подсветка выбранного участка, глубины и ДУ. Реальные высоты зданий и рельеф во входе отсутствуют. Вертикальное увеличение масштаба должно быть явно подписано и не менять расчёт. Наклон плоской карты сам по себе не показывает подземный профиль.

Рендерер выбирает №4 после небольшого прототипа на существующем React/MapLibre. Перед добавлением зависимости проверяются её актуальные API, лицензия и совместимость. Выбор конкретной библиотеки этим планом не навязывается.

Сцена получает объекты по существующим страницам API: явный предел количества отображаемых объектов, отмена старых запросов, обработка 413 и отсутствия WebGL с доступной 2D-картой/профилем. Для целого длинного пути за пределами bbox сначала проверить достаточность map API; если нужен отдельный endpoint пути, №4 описывает конкретный сценарий, №1 оформляет контракт до реализации.

**Готово:** интерфейс показывает настоящий рассчитанный профиль, а не произвольную глубину для всех труб.

## 7. Минимальный набор тестов для DEPTH

| Сценарий | Что проверяем | Основной владелец |
| --- | --- | --- |
| Без препятствий | Постоянные 3 м, K=1, стоимость при той же плановой сети совпадает с 2D | 3 |
| Газопровод | Проход сверху и снизу, просвет по габаритам; граничное допустимое значение и нарушение | 2, 3 |
| Кабель / существующая сеть | Просвет 0,5 м, реальная высота существующей сети по ДУ | 2 |
| Дорога / трамвай | Минимальная глубина, плановый угол и требуемая длина спецпрохода | 2 |
| Уклон | 0,10 допустим; превышение отклоняется; нулевая горизонтальная длина с перепадом недопустима | 2, 3 |
| Переход через 3 м | Правильное деление и стоимость примера 2→4 м из раздела 4 | 3 |
| Близкие препятствия | Общий изменённый уровень либо обоснованный отказ; выполнение всех просветов | 2, 3 |
| Разветвление | Согласованные глубины в общей камере по решению D1; расход/ДУ/стоимость общего участка | 2, 3 |
| Смена ДУ | Изменение габарита не ломает просвет, путь одного ДУ не обнуляется техническими узлами | 2, 3 |
| Недостаточный участок для перехода | Отклонение профиля, feedback и попытка другого плана | 2, 3 |
| Режимы и хранение | DEPTH-глубины конечные, 2D-глубины null; рейтинг раздельный; перезапуск сохраняет значения | 1 |
| Геометрия профиля | Промежуточные вершины используют долю накопленной длины; при развороте выбранного пути глубины меняются местами корректно | 4 |
| Карта и экспорт | Совпадают числовые/строковые ID, глубины, сводки и границы; выбор варианта не показывает старые данные | 1, 4 |
| Отмена и пределы | Прерывание освобождает ресурсы; достижение поискового предела не выдаётся за успешный DEPTH без профиля | 1, 2, 3 |

Тестовые координаты и количества объектов меняются между примерами. Работоспособность только на конкурсном GeoJSON не считается готовностью.
