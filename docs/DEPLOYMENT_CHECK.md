# Приёмка Compose и сохранности результатов

`scripts/check_restart_api.py` проверяет настоящие HTTP-результаты 2D и DEPTH до и после перезапуска backend. Перезапуск выполняет оператор или CI; сам Python-скрипт не управляет процессами, контейнерами и томами.

## Что проверяется

Фаза `capture` запускает обычную smoke-цепочку на `two-consumers` в 2D и `depth/gas-below` в DEPTH. Получаются четыре задачи: два успешных расчёта и две ошибки повреждённого JSON. Проверяются подключение всех целей, режим и глубины, совпадение карты/сводок с экспортом и отсутствие результатов у FAILED.

Затем сохраняются контрольные суммы статусов и диагностик, сводок, bounds, всех страниц input/result и ответов 409 для ошибочных задач. В snapshot находятся полные относительные пути запросов, включая курсоры, полученные до перезапуска. Экспорт проверяется отдельно по SHA-256 исходных скачанных байтов. Сравнение JSON-ответов не зависит от порядка ключей; десятичные значения читаются через Decimal.

Фаза `verify` только читает существующие задачи: все ответы и оба файла должны совпасть с сохранённым снимком. Новые задачи не создаются. На стандартных примерах сравниваются **28 HTTP-ответов и два GeoJSON-файла**. Удаление или подмена тома задач выявляется как ошибка, а не компенсируется повторным расчётом.

## Воспроизведение

Нужны Python 3.9+, Docker и Compose; порт 8080 должен быть свободен. Используйте отдельное имя проекта, чтобы не останавливать рабочий экземпляр:

```sh
docker compose -p heat-acceptance up -d --build
```

Дождаться HTTP 200 / UP на `http://127.0.0.1:8080/api/health`, затем:

```sh
python scripts/check_restart_api.py capture --snapshot /tmp/heat-restart.json --report /tmp/heat-capture.json
docker compose -p heat-acceptance down
docker compose -p heat-acceptance up -d
```

Снова дождаться UP и выполнить:

```sh
python scripts/check_restart_api.py verify --snapshot /tmp/heat-restart.json --report /tmp/heat-verify.json
docker compose -p heat-acceptance down
```

Для Compose 1.29.2 заменить `docker compose` на `docker-compose`. Между фазами нельзя применять `down --volumes`: результаты находятся в именованном томе `job-data`. Обычный `down` сохраняет тома. Snapshot должен иметь новый путь; `capture` отказывается перезаписывать существующий файл. Родительский каталог должен существовать. Другой сервер задаётся через `--base-url`; таймаут расчёта — `--timeout`, отдельного запроса — `--request-timeout`. Код 1 и `passed: false` означают ошибку.

Можно проверить и JAR без Docker: запустить backend с явным `--heat-network.jobs.storage-directory`, выполнить capture, остановить процесс, запустить снова с тем же каталогом и выполнить verify. Один каталог нельзя одновременно открывать двумя backend-процессами.

## Ubuntu CI

Workflow [compose.yml](../.github/workflows/compose.yml) запускается на pull request или вручную через Actions. Два независимых задания используют Ubuntu 22.04: текущий плагин Compose на runner и официальный бинарный Compose 1.29.2 с проверкой SHA-256 релиза.

Каждое задание:

1. Проверяет Compose config и собирает неизменённый `backend/Dockerfile`, включая `mvn verify` на Java 11.
2. Запускает backend и PostgreSQL через Compose, задаёт heap 512 МиБ только для этого стенда и ждёт health.
3. Выполняет capture, удаляет контейнеры через `down` с сохранением томов и запускает проект заново.
4. Проверяет, что ID backend-контейнера изменился, а имя подключённого тома задач сохранилось; выполняет verify.
5. Сохраняет snapshot, отчёты и журналы как `compose-<version>-reports` на семь дней. Удаляет только изолированный CI-проект и его тома; имя включает run ID, попытку и версию Compose.

Это проверка реального образа и пересоздания контейнеров. Она дополняет прежнюю проверку `docker compose config --quiet`, которая подтверждала только конфигурацию.

## Границы

- Проверяются завершённые SUCCEEDED/FAILED, а не прерывание активного расчёта. SERVER_RESTARTED и JOB_INTERRUPTED покрываются отдельными Java-тестами; этот сценарий не подтверждает восстановление после сбоя диска или питания.
- Статусы задач и сводки вариантов хранятся в PostgreSQL (том `postgres-data`), крупные файлы — в томе `job-data`. После verify CI проверяет строки `heat_jobs` и `heat_job_variants` и отсутствие JSON-файлов статуса в томе задач.
- Frontend не входит в текущий Compose; полноценное развёртывание пользовательского интерфейса остаётся отдельной задачей участника 4 и интеграции.
- Нет проверки входов 3 ГиБ, длительной нагрузки, измерения памяти, резервного копирования и восстановления на другой машине. Heap 512 МиБ не равен пику памяти процесса.
