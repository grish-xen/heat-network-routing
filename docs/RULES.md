# Правила задачи — актуальная версия

Основа: `reference/current-technical-appendix.docx` и `reference/clarifications.docx`. Этот файл — рабочая сводка; при споре смотрите первоисточник. `reference/original-case.pdf` содержит прежние требования к реконструкции, которые не применяются в актуальной расчётной модели.

## Вход

- Один GeoJSON `FeatureCollection` в EPSG:4326. Для длин, буферов и габаритов геометрия переводится в EPSG:32637.
- Обязательные типы: `source` (Point), `heat_network` (LineString, `diameter`), `heat_chamber` (Point), `oks_connection_point` (Point, `flow_tph`), `restriction` (LineString/MultiLineString/Polygon/MultiPolygon, `restriction_type`). У всех есть `id` и `object_type`.
- ID бывают строковыми или числовыми. Каждая `oks_connection_point` — отдельная цель. Полигон ОКС имеет `restriction_type = oks`; явной связи между точкой и полигоном нет.
- Проверочный набор будет другим: координаты, ID и количество объектов нельзя фиксировать в коде.

## Новая сеть

- От каждой подключённой точки к месту присоединения существует ровно один путь; замкнутых контуров нет. Общие участки для нескольких точек допустимы.
- Расход участка равен сумме `flow_tph` расположенных далее по сети точек; подающую и обратную трубы не складывают.
- Минимальный ДУ выбирается так, чтобы удовлетворять и расходу, и предельной длине по таблице 1 приложения. Произвольное завышение ДУ и его смена только для нового отсчёта длины запрещены. По направлению к присоединению ДУ не уменьшается.
- Предельная длина проверяется отдельно на каждом непрерывном пути одного ДУ. Общий участок учитывается в каждом пути; параллельные ветви не суммируются.
- Разветвления — только в камерах; не более четырёх примыканий на камеру с учётом существующих линий. Обычный поворот — вершина LineString, без отдельного узла. Изменение направления в одной точке не превышает 90°; лишние зигзаги недопустимы.
- Если выбранное место на существующей сети находится не далее 10 м от подходящей существующей камеры и лимит примыканий соблюдён, подключение идёт в неё. Иначе новая камера создаётся на существующей линии. Отдельного выходного объекта `tie_in` нет.
- Существующая сеть и камеры **не реконструируются**. Их текущий расход и резерв в обязательном расчёте не определяются.
- Не подключать точку можно лишь тогда, когда допустимый маршрут не найден; намеренно исключать её ради лучшего рейтинга нельзя.

## Ограничения и стоимость

- Обязательные типы ограничений: `oks`, `park`, `social_area`, `prohibited_site`, `water`, `railway`, `road`, `tram_tracks`, `gas_pipeline`, `power_cable`, а также пересечение существующего `heat_network` без присоединения. Точные отступы, углы, специальные участки и коэффициенты — таблица 2 приложения.
- Отступ измеряется до внешней границы расчётного габарита новой сети, то есть включает половину ширины пары труб. Для своего полигона ОКС разрешён один финальный прямой участок к целевой точке по правилу раздела 2.2 приложения. Трактовка команды «ближайшая достижимая граница» и проверка — [OWN_OKS_APPROACH.md](OWN_OKS_APPROACH.md).
- Специальный проход прямой; на его границах участок делится. При наложении проходов выполняются все геометрические требования, а для цены применяется наибольший `Kспец`.
- Стоимость новой сети: длина × ставка для ДУ × коэффициент специального прохода; в 2D коэффициент глубины равен 1. Новая камера стоит по шкале раздела 3.2 приложения и уже включает присоединение. Её ДУ определяется по всем примыкающим новым и существующим участкам. Каждый новый участок, заканчивающийся в существующей камере, даёт врезку за 5 млн руб.
- Штраф за ненайденный маршрут: `100 000 000 + 500 000 × flow_tph`. Итоговый показатель: `S = 0,7 × (calculated_cost / 25 000 000) + 0,3 × (new_network_length / 100)`. Меньше — лучше. Допускается до трёх содержательно разных вариантов.

## Глубина

Режим с глубиной необязателен и строится отдельно от 2D. В 2D геометрия двумерная, `depth_start` и `depth_end` равны `null`. Если режим с глубиной будет добавлен, используйте раздел 5 актуального приложения; варианты двух режимов не ранжируются вместе.

## Технические требования, сохраняющиеся из PDF

Ubuntu Server 22, Java 11, Spring Boot 2.6.3, springdoc-openapi-ui 1.7.0, docker-compose 1.29.2. В проекте выбран PostgreSQL 16 (ТЗ допускает PostgreSQL до 18 включительно или OpenSearch до 2.18). ОЗУ — 16 ГБ, до 50 пользователей, вход до 3 ГБ и результат до 500 МБ. Большие файлы обрабатываются потоково и через временное дисковое хранилище; для карты API отдаёт ограниченные страницы по области просмотра.

Числовые справочники обязательного 2D-режима находятся в `backend/src/main/resources/rules/catalog-v1.json`. Их соответствие DOCX проверяет `scripts/check_repository.py`; модули используют один каталог. Сам каталог не заменяет словесные правила этого приложения.

## Неточности первоисточника

В примере выходного GeoJSON раздела 7.3 отсутствует `length`, хотя таблица обязательных полей раздела 7.2 его требует. Экспортируем `length` по таблице. Значение `construction_cost` уже включает камеры и врезки — повторно добавлять их при расчёте `calculated_cost` нельзя.

Для полигональных дорог и трамвайных путей границы специального участка определены явно; вариант этих ограничений в виде линии отдельно не раскрыт. Если организаторы передадут такую геометрию, нужно согласовать границы специального участка. Не следует молча применять правило «полигон плюс 3 м» к линии. Этот вопрос не мешает работе с текущим набором и подготовке обязательной поддержки полигонов.
