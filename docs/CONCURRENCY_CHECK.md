# Одновременные клиенты: изоляция задач и результатов

## Запуск

Нужны Python 3.9+ без дополнительных библиотек и тестовый backend. Из корня репозитория:

```sh
python scripts/check_concurrent_api.py --clients 4
python scripts/check_concurrent_api.py --clients 50 --report ../concurrent-report.json
python scripts/check_concurrent_api.py --clients 4 --mode mixed
python scripts/check_concurrent_api.py --clients 2 --mode mixed --input test-data/competition-corrected.geojson --timeout 240
```

Сервер по умолчанию `http://127.0.0.1:8080`; другой адрес задаётся `--base-url`. Допустимо 1–50 клиентов; по умолчанию четыре. Каждый клиент создаёт две реальные задачи: корректный расчёт и повреждённый JSON. Поэтому полный прогон на 50 клиентах создаёт 100 задач. Они остаются в тестовом хранилище до штатного истечения срока. Скрипт не удаляет чужие задачи и не отменяет серверные расчёты при таймауте.

## Что проверяется

По умолчанию используется `--mode 2d` и маленький синтетический вход `two-consumers`: пять объектов и две точки подключения. `--mode depth` использует `depth/gas-below`, чтобы проверить меняющуюся глубину. `--mode mixed` чередует 2D и DEPTH между клиентами (при одном клиенте получается только 2D). `--input` задаёт один исходный небольшой файл для всех клиентов вместо этих примеров; ограничения smoke-скрипта на размер и число страниц сохраняются.

Долготы всех объектов смещаются на `номер клиента × 0,005°`; ID сохраняются одинаковыми между задачами одного примера. Это намеренно делает наборы различимыми по координатам и проверяет, что одинаковые ID не приводят к подмене данных между задачами. Генерация меняет только тестовые входы, координаты не зашиваются в рабочий алгоритм.

Подготовленные клиенты стартуют через общий барьер. Каждый выполняет [HTTP smoke-сценарий](API_SMOKE_TEST.md) в строгом режиме полного подключения: расчёт, сводки, скачивание, пагинация input/result, bounds и диагностика повреждённого JSON. Дополнительно:

- Все input-объекты из карты точно сравниваются со своим входом, включая координаты и свойства.
- Режим задачи и глубины соответствуют запросу; у стандартного газового DEPTH-примера профиль не постоянный.
- Конечные ID маршрутов содержат всех потребителей с сохранением типов, а координаты концов совпадают со своим входом с допуском 1e-9 градуса.
- Проверяется уникальность ID всех корректных и ошибочных задач.
- При двух и более клиентах курсор карты первой задачи отправляется во вторую: ожидается 400 / INVALID_CURSOR.
- Ошибки HTTP, включая 503, не скрываются повторной загрузкой: соответствующий клиент завершает проверку с ошибкой.

Результаты всех клиентов сохраняются при `--report`; в консоли — общая сводка и ошибки. `passed=true` и код 0 означают, что прошли все клиентские сценарии и проверки изоляции. Код 1 означает ошибку; `error` и `results` объясняют причину. `--timeout` (по умолчанию 180 секунд) и `--request-timeout` (15 секунд) имеют ту же семантику, что в smoke-скрипте.

## Проверенный локальный прогон 27 сентября 2026

Backend: сборка коммита `436bd36` (включает PR №11–13), Java 11, Windows, `-Xmx512m`. Отдельное хранилище, порт 18081, стандартные настройки: 2 вычислительных потока и очередь 48. Сначала четыре клиента, затем 50 на том же процессе. Дополнительных повторов из-за ошибок не делалось.

| Клиенты | Успешные сценарии | Весь прогон | p50 клиента | p95 клиента |
| --- | --- | --- | --- | --- |
| 4 | 4/4 | 3,733 с | 3,346 с | 3,385 с |
| 50 | 50/50 | 25,878 с | 23,985 с | 25,670 с |

Время клиента — весь сценарий после стартового барьера: очередь, расчёт, проверки результатов и карты, задача с повреждённым JSON и проверка изоляции входа. Это не чистое время алгоритма. Перцентили вычислены методом ближайшего ранга по одному прогону; данные не являются SLA. 512 МиБ — предел heap JVM, а не измеренный пик потребления памяти процесса.

Все корректные задачи подключили обе синтетические точки; ответы карты и экспорта совпали, курсор чужой задачи отклонён. Локальные полные отчёты вне репозитория: `.build-tools/concurrent-run/four-clients.json`, `fifty-clients.json`; журнал backend — там же.

## Проверенный смешанный прогон 29 сентября 2026

Backend после PR #23 (`main`, `ce5046a`), Java 11 / Windows, heap `-Xmx512m`, стандартные 2 рабочих потока и очередь 48, отдельное хранилище на порту 18084. Реализация backend и frontend не менялась. Повторов неудачных запросов не было.

| Нагрузка | Результат | Весь прогон | p50 клиента | p95 клиента |
| --- | --- | --- | --- | --- |
| 4 клиента: 2×2D и 2×DEPTH, стандартные малые примеры | 4/4 | 1,832 с | 1,723 с | 1,736 с |
| 50 клиентов: 25×2D и 25×DEPTH, стандартные малые примеры | 50/50 | 8,812 с | 8,081 с | 8,663 с |
| 2 клиента: конкурсный вход в 2D и DEPTH, у второго смещены координаты | 2/2, по 17/17 подключений | 40,431 с | 40,214 с | 40,297 с |

Проверены экспорт, постраничная карта, режим и глубины, все исходные объекты и конечные координаты маршрутов, уникальность jobId и отклонение чужого курсора. Каждый клиент дополнительно отправил повреждённый JSON и проверил FAILED/409. Отчёты локального прогона: `.build-tools/depth-service-run/mixed-four.json`, `mixed-fifty.json`, `competition-pair.json` (рядом с репозиторием). 50 клиентов создали 100 задач; вся серия вместе с частичными сценариями — 116 задач. Это один прогон, а не статистическая оценка производительности. Сравнивать время с историческим 2D-прогоном выше напрямую нельзя: наборы и версия решателя различаются.

Между малыми прогонами также прошёл `check_partial_api.py`: при запрете вокруг строковой цели `"2"` в обоих режимах подключена числовая цель `1`; статус SUCCEEDED сохраняет ROUTE_NOT_FOUND и SEARCH_BUDGET_EXHAUSTED. Неподключённая цель имеет расход 15 т/ч, штраф по каталогу составляет `100000000 + 500000 × 15 = 107500000` ₽ и входит в calculated_cost. Проверены совпадение сводок/карты с экспортом и отсутствие маршрута к заблокированной цели. Отчёт — `partial.json` в том же каталоге. Подробности сценария — [API_SMOKE_TEST.md](API_SMOKE_TEST.md).

## CI и ограничения

GitHub Actions запускает четыре клиента в режиме `mixed` после одиночной smoke-проверки против того же упакованного JAR с временным хранилищем и heap 512 МиБ. Затем проверяются частичные результаты обоих режимов через `scripts/check_partial_api.py`. Сценарии не требуют браузера.

50 клиентов — это одновременно работающие HTTP-клиенты; одновременно рассчитываются только две задачи, остальные ожидают очередь. Проверка не доказывает готовность к 50 файлам по 3 ГиБ, тяжёлым геометриям, длительному многократному потоку запросов, нехватке места на диске или массовым обрывам загрузки. Не проверено переполнение очереди более чем 50 запросами. Следующее нагрузочное испытание должно использовать целевую машину, репрезентативные большие входы и измерение памяти/диска/времени. Качество маршрутов конкурсного примера рассматривается отдельно.
