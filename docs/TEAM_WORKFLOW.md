# Совместная разработка четырёх участников

## Ответственность

| Участник | Папки / интерфейсы | Первая задача |
| --- | --- | --- |
| 1 — платформа и интеграция | `input`, `api`, `output`, Docker, БД | Загрузка → статус задачи; чтение маленького примера, проекция и Dataset |
| 2 — маршруты и геометрия | `routing`, RoutePlanner, SpatialValidator | Кандидат для простого примера без препятствий; геометрия и связи по контракту |
| 3 — инженерный расчёт | `calculation`, каталог правил | Вычислить пример с двумя целями: расходы, ДУ, камеры, стоимость и score |
| 4 — интерфейс | [`frontend`](../frontend/README.md), потребитель HTTP API | Загрузка/статус/карта/сравнение на файлах `test-data/api` и ожидаемом GeoJSON |

`model`, `contracts`, справочники и основные документы — общие. Участник 1 координирует изменения контрактов; каждый автор сам подключает свой модуль к общему приложению. Участнику 1 достаётся больше инфраструктурной работы: после первых задач участник 4 может помочь с экспортом и приёмкой API.

Согласование владельца проекта от 29 сентября 2026: участник 1 может самостоятельно исправлять реализацию и тесты модулей 2 и 3, фиксируя результат и проверки в PR. Отдельное предварительное согласование каждого исправления с участником 3 не требуется. Изменения реализации frontend участника 4 по-прежнему согласуются отдельно.

## После создания репозитория GitHub

Общий репозиторий — https://github.com/grish-xen/heat-network-routing. В нём лежит содержимое `heat-network-routing`, включая `.github`, `.gitignore` и `.gitattributes`; основная ветка — `main`. Владелец приглашает остальных через Settings → Collaborators. Работайте через Pull Request, с отзывом другого участника и успешной проверкой workflow `Verify starter` (job `backend`).

В закрытом личном репозитории GitHub Free эти правила соблюдаются по договорённости. Принудительная защита ветки для такого репозитория доступна с GitHub Pro; при его наличии включите обязательный PR, один отзыв и успешную проверку. Покупка подписки для начала разработки не требуется.

Каждый участник клонирует **один и тот же** репозиторий на свой компьютер. У всех есть весь проект, хотя основная работа ведётся в своих пакетах.

## Одна задача — одна небольшая ветка

```sh
git switch main
git pull --ff-only origin main
git switch -c feature/input-parser
# выполнить небольшую задачу и проверки
git add backend/src/main/java/ru/hackathon/heatnetwork/input
git commit -m "Add GeoJSON input parser"
git push -u origin feature/input-parser
```

После push автор открывает Pull Request в `main`, описывает поведение и проверки. Второй участник просматривает изменения; GitHub запускает CI. Затем PR сливается. Остальные забирают свежий main.

Если во время работы изменился main, в своей ветке выполните `git fetch origin`, затем `git merge origin/main`, исправьте конфликты, повторите проверки и push. Не используйте force push без согласования. При конфликте общих классов согласуйте смысл полей с автором другой ветки, а не выбирайте целиком одну из сторон.

## Частота интеграции

Не ждите завершения всего модуля. После одного небольшого поведения делайте PR. Каждый день запускайте общую цепочку. Первый рубеж — синтетический пример: загрузка → кандидат → рассчитанный вариант → экспорт → карта. Второй — препятствия и все обязательные правила. Третий — конкурсный и изменённые наборы, потоковая обработка, нагрузка и демонстрация. Дополнительный режим глубины идёт после обязательного 2D.

## Задача для ИИ

Передавайте ему свою задачу, `AGENTS.md`, актуальные правила, модель/интерфейсы и выбранный тестовый пример. Просите менять свой модуль и добавлять проверки его поведения. Изменение общей модели оформляйте отдельным согласованным PR, чтобы соседи успевали обновиться.

## Готовность стартового комплекта и продукта

Каркас задаёт контракты и компилируется. Продукт будет готов после реализации модулей, проверки соблюдения всех ограничений на других наборах, экспорта, карты, потокового ввода/вывода, запуска Compose на целевой Ubuntu и проверки нагрузки. Успешный health и зелёный CI каркаса не означают готовность алгоритма.
